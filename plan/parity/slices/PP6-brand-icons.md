# PP6 — The favicon and app icons

The shipped icons were the **pre-rebrand bunny**, on the pre-Pewter palette. Reported by the user
on 2026-09-02: "we don't need the old bunny favicon any more, all temari logo should use the new
one."

## What was actually wrong

Two separate problems, and only one of them was the drawing.

**`public/favicon.svg` was a different mark entirely** — a bunny: two ellipse ears, a clipped head,
a gold headband, dot eyes and cheeks, on `#241C54` indigo with `#F5F0E4` cream and `#D9A53C` gold.
It predates both the `TemariMark` arcs and Pewter. It was the only bunny left in the repo; the
sweep for its distinctive `head-clip` found nothing else.

**`resources/brand/logo/` already held the arc mark** — six SVGs, `temari-favicon`,
`temari-app-icon`, `temari-mark`, `-small`, `-mono` and `temari-lockup` — but all six were still
painted in the old indigo/gold/cream. So the logo did not need redrawing. It needed the palette it
should have had since the rebrand, and `public/` needed to actually use it.

## What ships

- **The six logo SVGs are recoloured**, slot for slot, not redesigned: `#241c54` → `#171f28`
  (sky), `#170f38` → `#0b1017` (sky-deep), `#d9a53c` → `#ade047` (horizon), `#f5f0e4` → `#f1f5f8`
  (cream). The one judgement call is `#ae8430`, a darkened gold used as the `--mark-lead` default,
  which becomes the vivid `#ade047` — because `TemariMark.tsx` draws its outer arc as
  `var(--color-horizon)` on **both** grounds, so the vivid fill is the brand's lead everywhere.
- **`public/favicon.svg` is now `temari-favicon.svg`**, byte for byte.
- **Every raster is regenerated from the same SVGs** by a new
  [`resources/brand/build-icons.mjs`](../../../resources/brand/build-icons.mjs):
  `apple-touch-icon.png` (180), `icon-192`, `icon-512`, `icon-maskable-512`, and `favicon.ico` at
  16/32/48. It renders through the container's own chromium, the same one `browser-review` uses.

**The arc counts are deliberately left alone.** `temari-app-icon` and `temari-mark` draw three
arcs; `temari-favicon` and `temari-mark-small` draw two, which is what `TemariMark.tsx` renders at
its 20-28px in-app sizes. That is a logo system — detailed at large sizes, simplified at small —
not an inconsistency, so flattening them to one drawing would have been a redesign rather than the
recolour that was asked for.

**Maskable needs no separate source.** In `temari-app-icon.svg` the mark occupies the middle ~55%
of the 1024 canvas, comfortably inside the 80% safe zone a maskable icon must respect, so the
`any` and `maskable` entries render from the same art.

## Two dead PWA shortcuts, fixed on sight

`manifest.webmanifest` declared three shortcuts, and **two of them pointed at routes that do not
exist**:

- `History` → `/activities`. `route:list` has only `activities/{activity}`; the feed lives at
  `/history`. This is the same wrong assumption that had been silently dropping activity detail
  from every `browser-review` sweep until `PP4` fixed the resolver.
- `Collection` → `/cards`. There is no such route and no collection page — P12 records that none
  ever existed.

`History` now points at `/history` and the `Collection` shortcut is removed. Its
`background_color` and `theme_color` were also still the old palette (`#F5F0E4` / `#ECE2CE`) and
take their Pewter counterparts, which incidentally makes the manifest agree with
`app.blade.php:78`'s existing `#e2e8ee`.

## Deliberately not touched

- **`og-default.png`.** It is generated by `build-og.mjs`, which reads `COLOR` from
  `build-tokens.mjs` and the path data out of `temari-mark.svg`, overriding the strokes itself — so
  it is already palette-current and my recolour cannot reach it.
- **Whether the PWA chrome should be dark.** The manifest carries one `theme_color`, the app
  defaults to the dark ground, and the light value is what `app.blade.php` has always declared.
  Repainting a stale colour is a fix; deciding the PWA should launch dark is a design call nobody
  has made. Recorded rather than taken.
- **`temari-lockup.svg`'s wordmark font.** It sets `Plus Jakarta Sans`; the shipped `BrandMark`
  renders the wordmark in `font-mono`. Same class of divergence, but it is a typography decision
  and the lockup file is not used by the app.

## Acceptance criteria

1. No bunny remains anywhere in the repo.
2. Every icon in `public/` derives from `resources/brand/logo/`, and re-running `build-icons.mjs`
   reproduces them.
3. `favicon.ico` is a valid multi-size container the browser actually accepts.
4. The manifest's shortcuts all resolve to real routes.

## Verification notes

- The rendered `icon-192.png` was **opened and looked at**, not just checked for a non-zero byte
  count: lime outer arc, cream inner arcs, dark ground, matching the in-app mark.
- `favicon.ico`'s container was parsed back out — three frames at 16/32/48, each a real PNG by
  magic number — rather than assumed well-formed because the writer did not throw.
- Every icon URL was fetched from the running app: `/favicon.svg` 200 `image/svg+xml`,
  `/favicon.ico` 200 `image/vnd.microsoft.icon`, `/icon-192.png` and `/apple-touch-icon.png` 200
  `image/png`, and the four `<link rel>` declarations resolve to exactly those paths.
- **Both manifest shortcuts were followed** and return 200. That is the check that would have
  caught them: the two dead ones had been declared for as long as the manifest has existed.

## Found, not fixed

`/manifest.webmanifest` is served as `text/plain` rather than `application/manifest+json`. Browsers
accept it, so nothing is broken today, but it is wrong. The fix is a static-file MIME rule in the
FrankenPHP Caddyfile, which is production configuration rather than application code, so it is
recorded here rather than changed from inside a brand-asset PR.
