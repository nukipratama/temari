# Plan — deterministic periodizer and the Plan tab

The training instrument's forward half: a rules-only periodizer that fills a per-day plan (`planned_sessions`), rendered on its own top-level `/plan` tab. **Rules own every number, the LLM owns voice only** (see the "Plan authorship" row in the v2 program's locked decisions) — every figure in this doc through "Season" below is deterministic; the one LLM layer, "Plan narration" at the end, only narrates verdicts the rules already reached and never computes anything itself.

## Two seams: one assembler for the page, pure inputs for the periodizer

Nothing outside `App\Services\Run\Plan` assembles the plan itself. Two entry points stand between the engine and its callers:

- **The page.** [PlanPageAssembler](app/Services/Run/Plan/PlanPageAssembler.php#L39) owns every prop `/plan` renders — race, baseline session count, the multi-week arc with the readiness clamp and volume redistribution applied ([::weeks()](app/Services/Run/Plan/PlanPageAssembler.php#L153)), the season trio, the adaptation explanation and the narration payloads. [PlanController::index()](app/Http/Controllers/PlanController.php#L29) decides only which of them Inertia defers. The assembler is bound `scoped()` because Inertia's partial reload runs the action a second time and three props want the same ensured season. Until then the controller reached for eleven `Run\Plan` primitives directly, the only consumer outside the namespace to do so.
- **The plan.** [PlanInputs](app/Services/Run/Plan/PlanInputs.php#L16) is the whole database read a regeneration needs — season window, active race and its projection, stated preferences, behavioral session count, the days the athlete pinned or already ran, and the adapter's verdict — gathered by [PlanInputsGatherer::forUser()](app/Services/Run/Plan/PlanInputsGatherer.php#L34). [Periodizer::rowsFor()](app/Services/Run/Plan/Periodizer.php#L105) turns those inputs into a row per calendar day and touches neither the database nor the clock; [::regenerate()](app/Services/Run/Plan/Periodizer.php#L70) is gather-then-persist over it. The arc's ramp, deload, taper and peak behaviour is therefore asserted against hand-built inputs in `tests/Unit/Services/Run/Plan/PlanInputsTest.php`, with the feature suite left to prove what only persistence can — that the season stays anchored across successive Mondays.

## Two modes, chosen fresh on every regeneration

[Periodizer::regenerate()](app/Services/Run/Plan/Periodizer.php) reads the user's active [[race-projection|race]] through [ResolveActiveRaceAction](app/Actions/Run/Plan/ResolveActiveRaceAction.php) — a `scoped()` memo, so the plan engine, the season service and the page's own controller share one read per request — and picks a mode. A mode switch (setting or clearing a race) takes effect at the *next* regeneration, never retroactively.

- **Race-oriented** ([PhaseSchedule::forRace()](app/Services/Run/Plan/PhaseSchedule.php)): **the race block is bounded by distance.** The block is 16 weeks ending on race week up to the half marathon, and 20 weeks past it, so `PhaseSchedule::blockOpensOn()` returns race week's Monday minus 15 or 19 weeks. Weeks from the season's start to block open run the self-scaled cycle below (`zone: general`), and only the weeks from block open to race day are periodized (`zone: block`). A block opening on or before the season's start covers the whole span. Block open is a computed date, never a season boundary. See [[the-block-opens-on-a-computed-date]]. Inside the block, taper length scales with race distance (1 week &le;15&nbsp;km, 2 weeks 15&ndash;25&nbsp;km, 3 weeks &gt;25&nbsp;km). Too little time to build anything (`weeksToRace &le; taperWeeks + 1`) skips straight to a taper-only arc. Otherwise the weeks remaining after the taper split `base 30% / build 45% / peak 25%` (peak and build each floored at 1 week, base absorbs the remainder so the three always sum exactly — no rounding drift). Build ramps volume ~7.5%/week compounding, **capped so no multiplier passes 1.4** (a 12-week block's 1.16 is untouched; 16 and 20 weeks are trimmed from 1.44 and 1.54, and a 52-week arc no longer reaches 3.42) — see [[a-goalless-arc-does-not-ramp]]; Peak holds build's final multiplier, so the long run climbs or holds until the taper; Taper reduces from it along a `-20% / -40% / -60%` curve (the nearest-to-race week always lands on the steepest cut, scaled for shorter tapers) — see [PhaseSchedule::volumeMultipliers()](app/Services/Run/Plan/PhaseSchedule.php). **Every fourth week of the base/build stretch is a scheduled recovery week**, so the ramp never compounds unbroken (five build weeks would otherwise be +33% with nothing absorbing it); Peak and Taper are exempt as reductions already, a ramp shorter than four weeks gets none, one that would land on the ramp's last week moves a week earlier so Peak always follows a Build week, and the ramp *resumes* from the level it reached rather than restarting after the dip ([[a-race-block-never-prescribes-below-habit]]). Until [[the-plan-follows-the-coaching]] the only deload here was the reactive one below, which fires after monotony or adherence has already slipped.
- **Self-scaled** ([PhaseSchedule::selfScaled()](app/Services/Run/Plan/PhaseSchedule.php)): no taper/peak exists without a race date to count back from, so it cycles a repeating 3-weeks-build : 1-week-deload mesocycle indefinitely, **holding flat at 1.0 with its deload weeks at 0.65** rather than ramping: the baseline already tracks the athlete's real trailing volume, so a ramp on top counted the same growth twice and prescribed 2.75x actual volume at 20 weeks. `volumeMultipliers()` takes the mode explicitly, since a phase sequence alone cannot say which produced it. See [[a-goalless-arc-does-not-ramp]]. **An arc that follows a race the athlete actually ran opens with one recovery week** before that cycle starts — `Season.opens_with_recovery`, set by [SeasonService::followsARaceAlreadyRun()](app/Services/Run/Plan/SeasonService.php) off the race *date* rather than `completed_at`, since a race called off or superseded leaves nothing to recover from. It is an extra week rather than one borrowed from the first build block, and it reuses `Deload` rather than gaining a phase of its own. See [[a-closed-race-earns-a-recovery-week]].

Both modes materialize up to `Periodizer::HORIZON_WEEKS` (12) weeks of rows; a race-oriented arc that resolves to fewer weeks simply writes fewer. A race arc ends with race *week*, not race day.

**The arc is counted from the season, then sliced** ([Periodizer::sliceFromCurrentWeek()](app/Services/Run/Plan/Periodizer.php)). Both modes build the whole arc from the `Season`'s own start week and compute `volumeMultipliers()` across all of it *before* taking the horizon's worth that starts at the current week. Counting the arc from "today" instead put the week actually being trained at index 0 every Monday, which is `1.0` in every phase but Taper — so Build, Peak and the scheduled Deload were only ever visible in the lookahead. The multiplier that survives the slice is stamped on each row (`planned_sessions.volume_multiplier`) rather than recomputed at render, because a render window reaching back three weeks cannot see where the season began. See [[the-arc-is-anchored-once]].

**Race week is shaped around the race.** [WeekPlanBuilder::raceWeekType()](app/Services/Run/Plan/WeekPlanBuilder.php) overrides the day template for the week the goal race falls in: race day is a [SessionType::Race](app/Enums/SessionType.php), the day before it is rest, and so is every day after it. Until [[the-plan-knows-its-race-day]] the race date reached [PhaseSchedule::forRace()](app/Services/Run/Plan/PhaseSchedule.php) and nowhere else, so race week was laid out as an ordinary tapered week — a Sunday marathon got a long run the day before it and `rest` on the day itself, and a Tuesday 10K got a tempo session ON the race. **Race day is prescribed at the athlete's own goal**: [SegmentGenerator::raceSegments()](app/Services/Run/Plan/SegmentGenerator.php) divides `goal_time_sec` by the race distance, so a 59:00 10K reads 5:54/km rather than the 5:44/km threshold band the pace zone alone would give. The band survives as the qualitative zone label. With no goal time behind the row — a past race, once `plan:close-finished-races` has retired the goal — the band's own pace stands in.

A `Race` row carries its own `race_distance_m` ([PlannedSession](app/Models/PlannedSession.php)) rather than reading the goal back at render time: `plan:close-finished-races` retires the `RaceGoal` at 00:04, *before* `plan:score-compliance` grades the day, so the goal is already gone by the time anything needs the distance. That distance is what [SegmentGenerator::coreKmFor()](app/Services/Run/Plan/SegmentGenerator.php) sizes the day from — the one session sized from outside the athlete's own training, and the one the volume redistributor never scales. [ReadinessClamp](app/Services/Run/Plan/ReadinessClamp.php) never downgrades a race at any ceiling.

## Shared session-structure logic

[TrainingBaseline](app/Services/Run/Plan/TrainingBaseline.php) reads the athlete's own recent behavior fresh on every call (never frozen): sessions/week from the trailing 6-week average run count (clamped 3-6), weekly volume from a **trimmed mean** of those six weeks (highest and lowest dropped), and the long run derived as a share of that volume — floored three ways in a race season, and capped by a race-distance band, by 150 minutes of easy running and by half the week's volume, whichever binds first. **The long-run floors are a starting point, not a jump** ([TrainingBaseline::longRunTargetFloorKm()](app/Services/Run/Plan/TrainingBaseline.php)): the block's target long run (the race distance below the marathon threshold, and the readiness distance for every race: 12 km for a 10K, 18 km for a half, 30 km for a marathon, bounded by the cap) is divided by the biggest **Build or Peak** multiplier the block reaches, so the athlete arrives there by running the ramp. Taper and Deload multipliers are reductions and never count; a block holding neither Build nor Peak gets no floor. **The volume floor** ([TrainingBaseline::volumeFloorKm()](app/Services/Run/Plan/TrainingBaseline.php)) lifts the baseline until the block's weeks average the season's frozen `volume_floor_km`, the athlete's plain twelve-week actual mean at season start, and the half-the-week cap is sized off the bigger of that and the anchor. A race season opened while a run inside the load guard's 42-day window still awaits hydration is stamped `increases_held`: its block runs flat, with no ramp and no long-run target floor, and its training weeks each match the floor until a regeneration finds that load scored. See [[a-race-block-never-prescribes-below-habit]]. **Those ceilings bind on the prescription too, not only on the baseline.** `forUser()` returns the tighter of the three as `long_run_cap_km`, and [SegmentGenerator::coreKmFor()](app/Services/Run/Plan/SegmentGenerator.php) bounds `baseline * multiplier` by it — the single point every session type is a fraction of. Applying them to the baseline alone let the volume multiplier walk straight through: a 52-week-out 10K prescribed a 31.1 km long run and a 20.2 km tempo. A separate `long_run_progression_cap_km` holds each planned Long to 110% of the longest completed run in the prior thirty days; it does not resize the other session types, and is absent when there is no recent run ([[recent-single-run-cap-stages-long-run-progression]]). The baseline is deliberately *not* the longest recent run: that let one outlier set every session in the week, since [SegmentGenerator::coreKmFor()](app/Services/Run/Plan/SegmentGenerator.php#L119) scales the whole week off this one scalar. See [[plan-volume-anchors-on-weekly-mean]]. An explicit [TrainingPreference](app/Models/TrainingPreference.php) row sits above that behavioral read, not beside it: a set `sessions_per_week` always overrides the behavioral average (bypassing its 3-6 clamp — 2 is a valid explicit choice, just not a valid *inferred* one), and with zero logged weeks *and* no explicit `sessions_per_week`, a stated `experience_level` seeds which cold-start `[sessions, km]` pair to use instead of one flat default for every brand-new athlete. Real logged behavior always wins the moment any exists, regardless of what was once claimed. `TrainingPreference.goal_type` carries no computational weight in this class or anywhere else in the periodizer — it's narration-flavor signal only, since `RaceGoal`'s presence/absence already fully selects the periodization mode below.

[WeekPlanBuilder](app/Services/Run/Plan/WeekPlanBuilder.php) turns one week's `(phase, sessionsPerWeek)` into a row per calendar day — a fixed day-of-week template per session count 2-6 (the last training day is always the week's `long` run), quality slots sized/typed by phase (**no quality at all below three sessions** — at two the long run plus a quality day is the whole week, leaving no easy running; never more than two hard days; Base: at most one Tempo once there's a session to spare; Build/Peak/Taper: Tempo + Interval at five sessions or more, and at four or fewer the single slot follows **projected race duration** rather than race distance, since the same 10K is a VO2max event for a 35-minute runner and a threshold event for a 70-minute one — under 50 min leans Interval, 70 min or more leans Tempo, in between Build develops VO2max while Peak/Taper sharpen at threshold, and no projection means Tempo; self-scaled training stays threshold-only throughout per its "1-2 threshold sessions" spec wording, having no race pace to sharpen for; Peak/Taper for a marathon-distance race narrows the quality block to one race-pace-specific Tempo slot; a race season's `zone: general` week trains by the Base rule above regardless of the `phase` the self-scaled mesocycle assigned it — race-specific interval work waits for the block, and the adapter's `quality_delta` cannot push it past one session either, the same exemption Base already has). Quality never lands on the day either side of the long run — that adjacency wraps the week, so a Sunday long run also protects the following Monday. See [[the-plan-follows-the-coaching]], everything else Easy, everything not training Rest. When `TrainingPreference.run_days`/`long_run_day` are both set, they replace the day template entirely for that user — the chosen weekdays become the literal training days every regenerated week, with the flagged day always the long run — rather than merely seeding it; `Periodizer::regenerate()` is the only caller that threads this override through. `WeekPlanBuilder` decides `session_type` only — no km, pace or segment structure enters generation.

[IntensityPrescriptionResolver](app/Services/Run/Plan/IntensityPrescriptionResolver.php) resolves the quality dose before segments are drawn. The row stores its hard minutes, pace band, resolved pace, race context and deterministic reason, so later rendering and grading read the coaching decision that was actually made rather than silently recomputing it from newer fitness. Phase targets are ceilings, not automatic doses: sparse history starts conservatively, a recent comparable `hit` progresses, `too_hard` steps down, and `missed`/`unknown` hold. The weekly allocator also reserves at least 70% Easy time and at most two hard days; when that reserve binds, the largest hard contribution gives way first.

[SegmentGenerator::forPrescription()](app/Services/Run/Plan/SegmentGenerator.php) lays that stored decision into the day's full ordered [SessionSegment](app/Services/Run/Plan/SessionSegment.php) list. The headline `distance_km` remains the whole outing: warmup, recovery, hard work and an explicit `easy` remainder add back to it, while a day too short for meaningful quality becomes one Easy block. Tempo keeps its phase-shaped blocks and Interval keeps whole repetitions. Marathon/ultra Long work is Easy opening, one late race-specific block, then a short Easy finish. **A cooldown is still never prescribed.** Without VDOT, the hard-day and phase caps still apply, but no invented weekly percentage or displayed pace target is created; segment distances remain unmeasured until a reliable sizing pace exists. See [[a-session-is-the-whole-outing]] and [[plan-recalibration-rewrites-history]].

## Editable, pinned, regenerated

A day can be moved (date) or skipped via [PlanController::update()](app/Http/Controllers/PlanController.php) (`PATCH /plan/sessions/{plannedSession}`). Skipping leaves the prescribed session as-is but pre-emptively excuses the athlete from being graded on it once the compliance pass reaches it. **Moving is a swap, not a re-date**: `planned_sessions` is unique on `(user_id, date)` and `WeekPlanBuilder` materializes all seven days of every week, so every in-horizon target is already occupied — `update()` trades what the two days prescribe, each keeping its own calendar slot, and pins both. Per-segment editing is not exposed: segments are reconstructed from the row's stored intensity prescription. Any explicit edit auto-pins the row (so the next regeneration doesn't silently revert it) unless the request explicitly passes `pinned: false`.

Pin, block (`session_type = rest`) and delete were **cut** by the prototype-parity program's `PS4` (decision P23 — the prototype draws Skip and Move and nothing else). The `DELETE /plan/sessions/{id}` route and the `session_type` validation rule are gone with them; `pinned` survives as internal plumbing, set by `update()` rather than by any UI. `Periodizer::regenerate()` reads every pinned row in the horizon *before* building any week and never assigns a row to a pinned date; `WeekPlanBuilder` also skips any date before `$today` so **past weeks are never touched**. Regeneration is weekly ([routes/console.php](routes/console.php), `plan:regenerate` at Monday 00:26, after the existing Monday 00:00-00:21 cluster) plus on-demand (`POST /plan/regenerate`), on any change that reshapes a plan — setting a race ([RaceController::store()](app/Http/Controllers/RaceController.php)), clearing one ([RaceController::destroy()](app/Http/Controllers/RaceController.php)), or editing training preferences ([TrainingPreferencesController::update()](app/Http/Controllers/TrainingPreferencesController.php)) — and once more at the end of onboarding ([OnboardingController::store()](app/Http/Controllers/OnboardingController.php)) so a first plan exists the moment a user finishes signing up. Before that it didn't: those two triggers meant an athlete who connected on a Tuesday met an empty Plan tab and Home's "No plan yet." card until the following Monday. Onboarding is the right moment because `EnsureOnboarded` routes every new user through it, and it is the first point at which the preferences that shape a week — run days, sessions per week, the race goal — exist. Strava's backfill may still be running then, so a first week can be sized from [TrainingBaseline](app/Services/Run/Plan/TrainingBaseline.php)'s cold-start seeds; the backfill chain's last link ([KickoffRecapsJob](app/Jobs/AI/KickoffRecapsJob.php)) regenerates the moment that history lands, rather than leaving the cold-start week standing until Monday. It is a regeneration, not a gate: a failed backfill, a Strava outage or a genuine beginner with no activities would strand a gated athlete with no plan at all. The first week is described **once**, by whichever of two racers finishes second: onboarding narrates only if `users.backfilled_at` is already stamped, and the connect chain's last link ([KickoffRecapsJob](app/Jobs/AI/KickoffRecapsJob.php)) narrates only if a plan already exists — see [[strava-connect]]. Both go through [PlanNarrationRequester::requestForFirstWeek()](app/Services/AI/PlanNarrationRequester.php), which never invalidates, so the interleaving where both fire re-bills nothing and no ordering leaves the week silent. Until one of them fires there is no `Analysis` row, and `payloadsForCurrentWeek()` omits a day with no row rather than shipping a `Pending` payload the UI would draw as a skeleton over work nobody queued. Regeneration works each athlete inside its own `try`/`catch`: one athlete's data must never cost every athlete after them their week, which is exactly what happened before — see below.

**A race the athlete has already run stops driving the plan.** `completed_at` was only ever stamped by [RaceController::store()](app/Http/Controllers/RaceController.php) superseding one goal with another, so a race nobody replaced stayed `active()` forever and the periodizer kept planning against a day in the past. Since [PhaseSchedule::forRace()](app/Services/Run/Plan/PhaseSchedule.php) counts the weeks *left* until race day and `diffInWeeks` is signed, that count went negative and `array_fill()` threw — and because `plan:regenerate` looped without a guard, the whole run died on the first athlete holding one. [CloseFinishedRacesCommand](app/Console/Commands/Run/CloseFinishedRacesCommand.php) (`plan:close-finished-races`, daily 00:04, ahead of both `plan:score-compliance` and `plan:regenerate`) now retires a finished race so the plan falls back to the self-scaled arc; `forRace()` floors its week count at one regardless, since four callers reach it; and the command contains a per-athlete failure rather than propagating it. The race row is never deleted — a past race is still the athlete's record.

Each regeneration deletes every unpinned, still-`planned` row across the *full* 12-week horizon before writing (not just the freshly-computed weeks), so a shrinking horizon — e.g. switching from self-scaled to a near-term race — cleans up stale far-future rows from the old mode rather than leaving orphans. A row that already carries a verdict is exempt and is not rewritten either: since [[a-day-is-scored-when-it-is-run]] compliance is persisted at ingest, so a regeneration triggered later the same day would otherwise delete the score today's run had already earned. Two things hang off a deleted row and [Periodizer::persist()](app/Services/Run/Plan/Periodizer.php) carries them across the delete rather than losing them: today's readiness clamp (`clamped_km`/`rest_clamped_at`, stamped by [RestClampRecorder](app/Services/Run/Plan/RestClampRecorder.php)) is copied onto the row that replaces it — [[the-eased-session-leads]] only holds if the clamp survives a same-day regenerate — and every `plan_day` [Feedback](app/Models/Feedback.php) row filed against a deleted id is deleted with it, so `/devtools/feedback` never lists a flag against a day nothing enforces anymore.

The exception is an explicit training-history recalibration. [PlanRecalibrationService](app/Services/Run/Plan/PlanRecalibrationService.php) recomputes stored stream summaries with current HR zones, rebuilds weekly aggregates, regrades past plan rows chronologically and regenerates the future plan. A unique per-user job runs after a profile or synced-zone change; `plan:recalibrate-history` provides the foreground rollout path with `--user` and `--dry-run`, and excludes the demo account. The Plan tab keeps the last coherent plan visible behind a quiet pending notice. Old plan-day narration remains visible but is marked stale until the athlete explicitly asks for a reread; recalibration itself spends no LLM tokens. See [[plan-recalibration-rewrites-history]].

### The plan reshapes now, the voice on a cooldown

A saved setting reshapes the plan immediately; only its narration waits. That covers setting a race, clearing one ([RaceController::destroy()](app/Http/Controllers/RaceController.php) — `/race` previously had no way to call a race off at all, so a wrong date was stuck until it passed while the plan kept building phases toward it; the goal is stamped `completed_at` rather than deleted, since an abandoned race is still part of the record), and editing training preferences. A race replaces the plan's whole structure (`PhaseSchedule::forRace()` supersedes the self-scaled arc, the season flips mode, the week's quality work changes with it), and run days decide the shape of every week `WeekPlanBuilder` emits — so saving either and seeing nothing happen until Monday made the setting look broken, while the race flash message said Temari would keep the plan honest against it.

Re-narrating a week costs an LLM call per day, and these are exactly the settings someone fiddles with repeatedly in one sitting, so those two paths go through [PlanNarrationRequester::requestForCurrentWeekUnlessCoolingDown()](app/Services/AI/PlanNarrationRequester.php) behind a `Cooldown::PLAN_NARRATION_WINDOW_SECONDS` window. It guards **only** the voice — gating regeneration too would leave an athlete training against an arc their own goal had superseded. The manual regenerate button (which has its own hourly guard and exists precisely to refresh the voice) and `plan:regenerate` call `requestForCurrentWeek()` directly and are unaffected.

While the voice is held back, a day whose [MaterialFingerprint](app/Services/AI/MaterialFingerprint.php) has drifted is **omitted from the payload** rather than shown, so the card never carries a blurb describing a plan the athlete has since changed. The same rule hides a day with no row at all: `Analysis::toPayload(null, ...)` reports `Pending`, which the UI draws as a skeleton — honest while a job is queued, false hope when none is. A `pending` row keeps its skeleton and a `failed` one keeps its empty state, because both are backed by something real.

## Readiness clamp — render-time, deterministic, not a narrator

This is the *within-the-day* half of the readiness reaction; the *within-the-week* half (a real deload) is in "Reacting to what actually happened" below.

[ReadinessClamp::apply()](app/Services/Run/Plan/ReadinessClamp.php) compares a stored session's implied intensity against the CURRENT [ReadinessCeiling](app/Services/Run/Metrics/ReadinessCeiling.php) and, when the stored session asks for more than the ceiling allows, returns a downgraded view plus one of a handful of short templated strings (e.g. *"Your form dipped, so today's the easy version instead."*). That string is a **permanent floor**, not a placeholder: it always renders, and a narrated line ([`plan_clamp_voice`](app/Services/AI/Narrators/PlanClampVoiceNarrator.php)) replaces it **in place** once one lands, so a step-down is never unexplained, there is no pending skeleton on a block that must always say something, and a paused or cost-capped day still reads correctly. The narration is requested from the two sites that already compute a ceiling — the ingest listener and the 00:01 briefing — never from a render. See [[the-clamp-explains-itself]]. [PlanController::index()](app/Http/Controllers/PlanController.php) applies it to **today's row only**: a future day's readiness isn't knowable today, and clamping a whole training block by this moment's fatigue would defeat periodization. The stored row is never mutated. For TODAY, before credit, the payload's headline never depends on whether the ease was **recorded** by [RestClampRecorder](app/Services/Run/Plan/RestClampRecorder.php): `session_type`, `segments` and `distance_km` stay the stored session either way, and the eased version — recorded or merely advisory — ships beside them as its own `clamp` object, a marked step-down, carrying the clamp line as its reason ([[todays-ease-stays-a-stepdown]]). Only a **PAST** day's recorded ease is the day's session ([[the-eased-session-leads]]): `session_type`, `segments` and `distance_km` become the eased session read through [EffectiveSession](app/Services/Run/Plan/EffectiveSession.php), with `eased_from` naming what it replaced. Either way the headline is what the scorer grades. Both the render path and [RestClampRecorder](app/Services/Run/Plan/RestClampRecorder.php) hold off entirely — no clamp at all — while the athlete's recent load is still unscored ([HydrationBacklog::recentLoadAwaitsScoring()](app/Services/AI/HydrationBacklog.php)), so a half-hydrated post-connect history never bottoms the ceiling out at Rest for the wrong reason. [CurrentWeekPlanBuilder](app/Services/Run/Plan/CurrentWeekPlanBuilder.php) applies the identical clamp for Home's own current-week read (the `weekPlan` Inertia prop, `DashboardController`) — the two never disagree about today's row because they call the same `ReadinessClamp::apply()`.

Quality work (Tempo/Interval) needs the optimistic `QualityOk` ceiling; a Long day only needs `ModerateOk` (it's a volume day, not an intensity one); Easy needs the floor above `Rest`.

**A pace-only ease for the two cases `apply()` leaves untouched.** An Easy day that already clears `EasyOnly`, or a Long day that already clears `ModerateOk` (marathon-pace long runs included), gets no type/distance downgrade — but only just clears it, so [ReadinessClamp::paceEaseApplies()](app/Services/Run/Plan/ReadinessClamp.php) still asks for a gentler pace: the slow end of the easy band, [TrainingPaceCalculator::easySlowEndSecPerKm()](app/Services/Run/Metrics/TrainingPaceCalculator.php) exposing the 72% fraction the averaged `easy` figure already blends in, without moving that average. [RestClampRecorder](app/Services/Run/Plan/RestClampRecorder.php) records it once, the same way as `clamped_km`/`rest_clamped_at`, onto `planned_sessions.eased_pace_sec_per_km`, and [EffectiveSession](app/Services/Run/Plan/EffectiveSession.php) reads it back (`isPaceEased()`): type and core km are untouched, only the pace `PlanRenderer::dayPayload()` builds the day's segments with. It is rule-based only — no `plan_clamp_voice` request and no `DayClampedNotification`, since the day it applies to is exactly the boundary case [ClampNarrationContext](app/Services/Run/Plan/ClampNarrationContext.php) also has nothing to explain for — and grading is untouched, since [SessionIntentJudge](app/Services/Run/Plan/SessionIntentJudge.php) grades easy/long against marathon pace, never the easy prescription. See [[the-eased-session-leads]].

**A day shows no read until it is credited, and re-narrates exactly once to earn it** (#939, "Temari's read", superseding the ahead-of-time `plan_day_voice` label this paragraph used to describe). Before a run lands the day shows no `plan_day_voice` block at all — no row, no request, no skeleton; once it is credited the block appears as a coach's read of what happened (*"easy all the way at 6:43/km, with a pickup at the end; the tempo block never happened."*), phrasing [SessionIntentJudge](app/Services/Run/Plan/SessionIntentJudge.php)'s verdict from [[a-day-is-graded-on-distance-and-intent]] rather than re-deciding it. [PlanDayTool](app/Services/AI/Agent/Tools/PlanDayTool.php) carries `status`, `completed_km`, `ran_anyway` and, when there was a session to judge, `intent`/`intent_evidence` **only** once the day is credited — absent rather than null, since a key that is always present teaches the model the day is over when it is not. The intent verdict is read straight off the `PlannedSession` row (`intent_verdict`/`intent_evidence`, written by [ComplianceScorer::applyVerdict()](app/Services/Run/Plan/ComplianceScorer.php)) rather than recomputed, so the read can never disagree with the grade. The re-narration is driven by the existing fingerprint gate: [MaterialFingerprint::forPlannedSession()](app/Services/AI/MaterialFingerprint.php) adds `status` and `intent_verdict` **conditionally**, the same trick `race_distance_m` uses, so an ungraded day keeps the digest it already carries and shipping this re-narrates nobody's week. The compliance *score* is deliberately excluded: it moves with every run that lands, while the verdict is what changes the sentence. [DispatchPostRunAnalysis](app/Listeners/DispatchPostRunAnalysis.php) calls [requestDayVoiceIfChanged()](app/Services/AI/PlanNarrationRequester.php) right after `creditIfEarned()`, guarded to today's runs like the clamp voice beside it, and only once the day is actually credited — this is the *only* site that ever dispatches `plan_day_voice` to the LLM. Two consequences: a backfilled day never rewrites history at LLM prices, and a second run the same day re-narrates **only if it moves the verdict or the intent** (`partial` -> `done`, `done` -> `overreached`, `hit` -> `missed`) — a run that improves the score inside its own band asks for nothing, because the score is not in the digest. That is the gated counterpart to `requestDayNarration()`, which invalidates unconditionally because a user edit *is* the change — though an edit only re-narrates when the touched day is itself already credited, since an edit almost always touches a day still ahead. Every past day of the current season gets the same read filled in rule-based, never the LLM, by `plan:regrade-season` — see "Plan narration" below.

**Once the day is credited the step-down disappears.** [Readiness::assess()](app/Services/Run/Metrics/Readiness.php) caps to `EasyOnly` on `ranToday` alone, so finishing the session is itself what clamps it: a tempo run at 102% rendered beside *"today backs off to easy"*, which reads as though the athlete should have done less. It once became a menu for a second outing instead; nobody asked for one. [PlanRenderer::dayPayload()](app/Services/Run/Plan/PlanRenderer.php) now ships `clamp: null` on a credited day, and the day states its own result through `judgedDayResult()` in [lib/plan.ts](resources/js/lib/plan.ts) — the recorded prescription against what was run. The narrated `plan_clamp_voice` line goes with it: it was written for the forecast, and re-narrating would bill an LLM call from a GET. See [[a-credited-day-shows-its-result]].

## Volume redistribution — a recompute, not a day-swap

Rather than moving a specific day's volume to another specific day (which risks an awkward doubled-up load), every `/plan` read recomputes the current week's remaining unpinned, non-past training days from `(week's target km) - (already completed) - (pinned days' km) - (today's now-fixed km)`, and applies a single continuous scale factor to each remaining day's own core km — see [VolumeRedistributor::redistribute()](app/Services/Run/Plan/VolumeRedistributor.php). No band bucketing: `SegmentGenerator` already accepts an arbitrary target distance for any session type, so a redistributed day lands on its exact scaled figure rather than snapping to a small set of discrete sizes. A recorded ease lowers both the week's target and today's fixed contribution by the same effective km, so its lost volume is not pushed onto the days after it. An unrecorded clamp still subtracts its smaller fixed contribution from the un-eased target, the same way a completed run would be. This, too, is render-only.

The scale factor is capped at `VolumeRedistributor::MAX_SCALE` and floored at `MIN_SCALE`, deliberately asymmetric. A week missed until Friday would otherwise land its whole target on the two days that remain, which is the cram week the rest of the engine's clamps exist to prevent; past the cap the volume is **written off rather than carried**. In the other direction the only floor used to be zero, so a week run ahead of its own menu could scale every remaining day out of existence — reducing should be harder than adding, so no remaining day drops below 70% of what it would otherwise ask. Volume never crosses a week boundary either — a missed week becomes a re-entry deload (below), not a debt added to the next one.

## Reacting to what actually happened

The three sections above are all *render-time* reactions within one week. The generation-time reaction is [PlanAdapter](app/Services/Run/Plan/PlanAdapter.php), which [Periodizer::regenerate()](app/Services/Run/Plan/Periodizer.php) consults before it builds a single week.

**Matching runs to sessions — written when the day is earned, settled when it ends.** Both paths go through [ComplianceScorer](app/Services/Run/Plan/ComplianceScorer.php), which is one class because the trailing-week context window it builds is load-bearing (see below). At ingest, [creditIfEarned()](app/Services/Run/Plan/ComplianceScorer.php) writes a day's verdict the moment a run lands on it, but **only ever upward** — anything short of credited stays `Planned`, so a partial day can never freeze low, while a run arriving after the daily pass already wrote the day off still lifts it. See [[a-day-is-scored-when-it-is-run]]. [ScoreComplianceCommand](app/Console/Commands/Run/ScoreComplianceCommand.php) (`plan:score-compliance`, daily at 00:09, before the Monday 00:26 `plan:regenerate`) then settles what is left: every still-`Planned` row that's now past-due, writing back `status`, `compliance_score` and `ran_anyway` via [SessionMatcher::scoreRange()](app/Services/Run/Plan/SessionMatcher.php). It doubles as the backfill mechanism for any historical backlog — the query is "any Planned row that's now past, regardless of age," so there's no separate backfill command. [SessionMatcher::scoreFor()](app/Services/Run/Plan/SessionMatcher.php) grades km actually run against km prescribed as a continuous `round(completedKm/plannedKm * 100)` score. **Each session type is credited by what it asks of the athlete.** A `Tempo` or `Interval` day counts its **best single run**, since the stimulus is one continuous effort and two easy outings are not a tempo session. A `Long` day **sums** its runs, because that volume genuinely accumulated, but reaches `done` only when one run carried `LONG_RUN_SINGLE_RUN_FRACTION` (70%) of the ask — otherwise the score keeps the honest ratio while the status reads `partial`, and the row carries a line saying the distance arrived in pieces. `Easy`, `Rest` and `Race` days sum, unchanged. Both figures come off one query in [completedKmByDate()](app/Services/Run/Plan/SessionMatcher.php), and the matcher reads each date's own session type itself so the three callers building `plannedKmByDate` cannot drift out of step with it. See [[a-credited-day-shows-its-result]]. The bands: `<35` is `missed`, `35-84` is `partial`, `85-129` is `done`, `>=130` is `overreached` (see [PlannedSessionStatus](app/Enums/PlannedSessionStatus.php); `isCredited()` counts `done`/`partial`/`overreached`, not `planned`/`missed`/`skip`). **A credited day is then judged on the session's intent too.** [SessionIntentJudge](app/Services/Run/Plan/SessionIntentJudge.php) reads the effective session's pace targets against the day's runs (best-effort windows for tempo, laps for intervals, overall pace against marathon pace for easy and long, heart rate able to rescue a slow block) and returns `hit`, `missed`, `too_hard` or `unknown`; [SessionMatcher::withIntent()](app/Services/Run/Plan/SessionMatcher.php) folds it in, so a `done` distance that missed its intent reads `partial` with its score capped at 84, running too hard reads `overreached`, and `unknown` grades on distance alone. The plain km ratio is kept beside it as `distance_score`. See [[a-day-is-graded-on-distance-and-intent]]; `plan:regrade-season` regrades the current season's past days under that rule. A day the athlete pre-emptively excuses (`PATCH /plan/sessions/{id}` with `skipped: true`) always resolves to `skip` regardless of km, with a null score — as does a day the readiness clamp downgraded to a full rest, via [PlannedSession::isExcused()](app/Models/PlannedSession.php). That second case has to be *recorded* rather than recomputed: the ceiling is derived from `TrainingLoad::summary()`, which counts the day's own runs, so the clamp that fired at 08:00 no longer exists at 00:09. [RestClampRecorder](app/Services/Run/Plan/RestClampRecorder.php) writes `rest_clamped_at` wherever the ceiling is already being computed — the ingest listener and the 00:01 briefing, never a render — so an athlete who took the rest the card prescribed isn't graded against the session it replaced. Only the full-rest clamp needs this; the other downgrades leave enough km on the day to credit on their own. That same write is where the athlete is told: it fires a `plan_clamp` inbox row ([[notification-inbox]]) carrying the clamp's own explanation, so a step-down is a record rather than something that existed only while the plan page still rendered it. A rest day asks for nothing, so it always reads `done` with a null score; `ran_anyway` separately records whether an activity was logged on it anyway, without changing the status. [PlanController](app/Http/Controllers/PlanController.php) and [CurrentWeekPlanBuilder](app/Services/Run/Plan/CurrentWeekPlanBuilder.php) read the stored `status` column as the primary source of truth; `SessionMatcher::statuses()` is the render-time fallback for the rare row still `Planned` despite being past-dated (the daily command hasn't reached it yet) **and for today, which the daily command deliberately never reaches**. Today is graded on the same km ratio but only ever upward — anything short of credited floors back to `Planned`, since falling short isn't decidable until the day ends while clearing the bar can't be undone by the hours left in it. That resolution is render-only; the persisted column is still written once, the morning after. See [today-credits-when-earned](docs/decisions/today-credits-when-earned.md). [PlanAdapter::previousWeekAdherencePct()](app/Services/Run/Plan/PlanAdapter.php) averages last week's persisted `distance_score`, never the intent-widened score (each day capped at 100 first, so one `overreached` day can't mask other missed ones), excluding rest, still-unscored and `skip` days, and defaults to perfect adherence when nothing was scoreable at all.

**One decision per week, safety first.** [PlanAdapter::decide()](app/Services/Run/Plan/PlanAdapter.php) is pure and returns exactly one [AdaptationReason](app/Enums/AdaptationReason.php), evaluated in priority order: readiness bottoming out at `Rest`, then monotony at Foster's injury-risk threshold, then weekly strain past a multiple of CTL, then a mostly-missed week, then a week run harder than it was written, then missed key stimulus, and only then race-pace feedback. Chasing a goal time can therefore never talk the plan past a red flag.

**A judged day states what it asked and what was run.** Prescribed km is not stored on the plan row: [PlanController::index()](app/Http/Controllers/PlanController.php) recomputes it on every load against the athlete's *current* baseline, which is right for the week ahead and wrong for a week already graded. [ComplianceScorer](app/Services/Run/Plan/ComplianceScorer.php) therefore measures each day against the baseline **as it stood that day** (`TrainingBaseline::forUser()` has always taken an `asOf`; nothing passed a historical one), and records the figure in `planned_sessions.prescribed_km` beside the verdict. A judged day then pairs the two facts by side rather than by figure — *"asked 6 km · 5:32/km"* then *"ran 5 km · 6:43/km"* in [WeekDayRow](resources/js/components/plan/WeekDayRow.tsx) via the shared `AskedRanResult` (see [resources/js/components/plan/DeltaPair.tsx](resources/js/components/plan/DeltaPair.tsx)) — both recorded facts, each labelled, no arrows since an arrow means the plan changed and this is what happened, so the pair still reads correctly when the athlete went long (*"asked 9 km"* / *"ran 12 km"*) — while a day still ahead shows the ask alone, prescription first in both. Without the as-of baseline a day scored weeks late was graded against fitness the athlete had since built: a fixture with two accumulated weeks marks a 3.4 km day against 14.3 km. Once the day is credited, its pace pairs up the same way: [SessionMatcher::ranPaceSecPerKmFor()](app/Services/Run/Plan/SessionMatcher.php) reads moving time over distance across the identical runs `creditedKm()` grades the km with — the best single run for Tempo/Interval, the day's total otherwise — so the asked line's pace is the effective target and the ran line's is the credited runs' own pace, never the two mixed on one line.

**A real deload, not a note.** The first four reasons rewrite the current week's phase to [PlanPhase::Deload](app/Enums/PlanPhase.php) before any row is built. That is structural in both directions at once: `WeekPlanBuilder` emits no quality slots for a `Deload` week, and because the rewrite lands *before* `volumeMultipliers()` runs over the arc, the week's km drop to `previous build's final multiplier * 0.65` with no separate scale factor to keep in sync — and the weeks after it stop counting the turned-down week as a Build week. A `Taper` week is exempt — it is already a planned reduction counting down to race day.

**A missed week comes back smaller.** Adherence below `MISSED_WEEK_ADHERENCE` produces the same deload rather than carrying the missed volume forward. Simulated end to end in [tests/Feature/Plan/MissedWeekAdaptationTest.php](tests/Feature/Plan/MissedWeekAdaptationTest.php): a 4-session, 28.3 km build week with nothing logged against it is followed by a 16.6 km deload week carrying zero quality sessions.

**A week run harder than it was written drops a quality session.** The adapter reads *how* last week's sessions were executed, not only whether they were done. [PlanAdapter::previousWeekExecution()](app/Services/Run/Plan/PlanAdapter.php) counts the days whose runs came in harder than the day prescribed: an `Easy` day that spent more than `EASY_DAY_HARD_SHARE` of its moving time above Z2 (via [StreamSummary::hardZoneShare()](app/Services/Run/Metrics/StreamSummary.php)), or a `Long`/`Tempo`/`Interval` day whose decoupling ran past [DecouplingBands::HIGH](app/Services/Run/Metrics/DecouplingBands.php), the one place the repo decides what a decoupling figure means. At `RAGGED_DAYS_MIN` such days the week returns `RanTooHard` with a `quality_delta` of -1. One merely ragged day is a bad morning and is ignored.

Past that, the two signals are weighed differently, and deliberately so. A **single** easy day above `EGREGIOUS_EASY_DAY_HARD_SHARE` of its time over Z2 is the whole verdict on its own; **two** days past `DecouplingBands::EGREGIOUS` (`EGREGIOUS_DECOUPLING_DAYS_MIN`) are needed before decoupling can say the same. The asymmetry is about what each number is. Time above Z2 is a bounded share of measured minutes, and the real prod week that put the single-day bar there rested on such a day: one Saturday missed and one Sunday long run spending 92.2% of its moving time in Z3 and above, scoring exactly 50% adherence — not *below* `MISSED_WEEK_ADHERENCE` — so a count-only rule called that week `steady`, "nothing to change, the plan stands". Decoupling is a ratio between two derived halves, and the *other* number quoted from that same week, 47.1%, turned out to be a strap dropout read as cardiac drift. Its inputs are guarded now (see [[stream-analysis]]), but a computed ratio does not get to remove an athlete's only quality session on the strength of one day.

Because sessions are matched to days and not to runs, a day counts once however many runs it holds. A run carrying no heart-rate stream reads as *no signal* rather than as a clean day: the zone breakdown is absent, and decoupling is withheld above a sustained 15% grade where the grade adjustment stops being trustworthy, so neither test can fire. This is deliberately **not** a deload: the volume stands, only the intensity comes off. It sits above race-pace feedback, so an athlete behind their goal time who ran the week too hard gets one *less* quality session, not one more — which is also why one decoupled day no longer hides that arm entirely.

**The race goal moves the sessions.** With an active race, [RiegelProjector](app/Services/Run/Metrics/RiegelProjector.php)'s projected finish is compared to the stored `goal_time_sec`. Outside `RACE_GAP_MARGIN` in either direction the adapter returns a `quality_delta`, which `WeekPlanBuilder::build()` applies to every week's quality block: behind the goal adds a session, inside the goal removes one. The addition is bounded by what the week can actually hold, so the banner never promises a day that never appears: it needs at least `MIN_SESSIONS_FOR_ADDED_QUALITY` (4) sessions — at three, the long run plus two quality days leaves no easy running at all — and it is capped by the number of training days left once the long run and its flanks are excluded, which is what holds a five-session week at the two quality days it already had. `Deload` and `Taper` weeks are exempt in both directions. Season-goal generation deliberately keeps using the unadapted `qualitySlotCount()`, so a mid-season adaptation doesn't move the goalposts it was scored against.

**Volume and stimulus are separate adaptation signals.** `adherence_pct` averages the prior week's capped `distance_score`, while `stimulus_adherence_pct` counts judgeable Long, Tempo and Interval verdicts from [IntentVerdict](app/Enums/IntentVerdict.php). A full-distance easy run on a quality day therefore completes volume but records a missed stimulus. One such miss holds the quality block; repeated misses or a key week where every one of at least two judgeable sessions missed removes one slot. `Unknown`, unscored and explicitly skipped rows are not misses, and the effective session after a readiness clamp is what the intent judge evaluates. See [[plan-adaptation-responds-to-stimulus]].

**Being ahead does not touch the quality block at all** (#933). Being ahead of a goal time is fitness feedback on a prescription that is working — the plan already self-corrects in the athlete's favor since prescribed paces derive from recent performance — not a red flag, so `AheadOfRacePace` carries `quality_delta: 0` the same as `Steady`. Removing a session on top of a faster prescription pushed the wrong way twice, and on a four-session week (a single quality slot on the phase baseline) it read as the plan asking an athlete *beating* their goal to stop training for it. Only `RanTooHard`, a real fatigue signal from [PlanAdapter::previousWeekExecution()](app/Services/Run/Plan/PlanAdapter.php) below, still empties the block. The `AdaptationReason` case stays and is still surfaced (headline "ahead of pace") so the athlete and the narrators can tell it apart from an ordinary `Steady` week, and so [SustainedAheadOfRacePace](app/Services/Run/Plan/SustainedAheadOfRacePace.php) can watch for it holding — see "Season narration" below.

**Recorded, not recomputed.** The verdict is written to a [PlanAdaptation](app/Models/PlanAdaptation.php) row, `unique(user_id, week_start)`. `/plan` reads that row rather than re-deciding, so a deload triggered on Monday still explains itself on Thursday after the athlete's readiness has recovered. When the deload takes a race season's week under its volume floor, the row also carries that floor as `volume_floor_km` and the detail line names it: the floor is a target the load guard may break, but never silently. A block holding its increases for unscored load stamps `increases_held` on the row the same way, and the detail line says the build is waiting. The copy lives on the enum ([AdaptationReason::headline()/detail()](app/Enums/AdaptationReason.php)), never in the database.

**Material evidence reconciles the current plan.** [ReconcilePlanAfterActivityIngested](app/Listeners/ReconcilePlanAfterActivityIngested.php) and [ScoreComplianceCommand](app/Console/Commands/Run/ScoreComplianceCommand.php) mark a user's earliest affected date through [PlanReconciliationService](app/Services/Run/Plan/PlanReconciliationService.php). [ReconcilePlanJob](app/Jobs/Run/ReconcilePlanJob.php) coalesces concurrent activity, uses a per-user lock, and calls [Periodizer::regenerateIfChanged()](app/Services/Run/Plan/Periodizer.php); unchanged adaptation fingerprints do not rewrite the plan. The Monday regeneration remains the recovery path for anything missed by the event or daily pass.

**Prescriptive, not clinical.** The Plan tab renders a standing not-medical-advice disclaimer on every load, adaptation or not ([Plan.tsx](resources/js/pages/Plan.tsx)): its own headed card, set at the supporting-body tier, with a link out to the full scope. Since `PS4` it sits at the foot of the page rather than above the timeline — the prototype draws no disclaimer at all, and the foot is the nearest place that keeps it without displacing a section the prototype does draw. Both the heading and the body are served from [TrainingDisclaimer](app/Support/TrainingDisclaimer.php) rather than held locally, so the public [[legal-pages]] and this tab cannot drift into two different positions. The tone gets to be assertive about numbers precisely because the clamps above stay in force underneath it.

## Render-time segments — never frozen into the row

[SegmentGenerator::coreKmFor()](app/Services/Run/Plan/SegmentGenerator.php) is the only place a `session_type` becomes an actual kilometre figure, combining the athlete's *current* long-run baseline with a phase-derived volume multiplier — the direct successor to `DistanceBandKm::kmFor()`, before `distance_band`/`pace_band` were retired as stored columns. [PlanController::index()](app/Http/Controllers/PlanController.php) recomputes this fresh on every page load (never reading a stored km), so a week regenerated weeks ago still displays honestly against the athlete's fitness today. `SegmentGenerator::generate()` goes one step further for the full segment breakdown: even the *shape* of an Interval day (its rep count) is pace-dependent, so nothing about a day's structure is ever persisted — see the "Shared session-structure logic" section above. The one number generation does stamp is `volume_multiplier`, and it is not fitness: it is where the week sits in its season's arc, which no render window can re-derive.

**Shared with Home, not duplicated.** [PlanRenderer](app/Services/Run/Plan/PlanRenderer.php) holds the two computations above — the phase→volume-multiplier grouping and the per-day payload — extracted out of `PlanController` so [CurrentWeekPlanBuilder](app/Services/Run/Plan/CurrentWeekPlanBuilder.php) (Home's `weekPlan` prop, no lookahead, no redistribution since Home never shows a future day's resized volume) can never numerically drift from Plan's own figures for the same week: a Peak/Taper/Deload week's multiplier is relative to how far into the season's arc the week sits, which both callers now read off the row itself. **A week reads its phase and multiplier off one row** ([PlanRenderer::weekRow()](app/Services/Run/Plan/PlanRenderer.php)): the latest-dated unpinned row, falling back to the latest-dated row when the whole week is pinned. Regeneration never rewrites a pinned row, a settled one, or a date already behind it, so a week can hold a stale row from an older generation beside fresh ones — a pinned Monday still reading `Build` while the adapter has just turned the week into a reactive `Deload`, or Monday to Thursday run under `Build` when a Friday on-demand regeneration deloads the rest. Every regeneration writes forward to the week's end, so the last row it could still own is the one carrying its most recent decision; reading the first row by date, as this used to, let one stale Monday cancel the deload on every surface, and a majority vote would let the four already-run days do the same. The phase-sequence recompute stays as the fallback for a window still holding a row written before generation stamped the multiplier, and it is why both callers query the identical `HISTORY_WEEKS` window.

## Season — the arc this plan belongs to (Slice 7)

The Plan tab's top-of-page summary section is the same periodized arc viewed at a higher zoom, not a separate page (`Season IS the training block` — see the v2 program's locked decisions). [SeasonService::ensureCurrent()](app/Services/Run/Plan/SeasonService.php) is called both from `PlanController::index()` (a fresh user's first page view already has a season) and from `Periodizer::regenerate()` (the weekly job and on-demand regeneration keep it in lockstep with the plan's own mode). `SeasonService::peekCurrent()` is the read-only counterpart the [[profile]] page uses instead — it returns the current season if one already exists, `null` otherwise, and never creates, updates, or closes a `Season` row. A self-scaled `Season` runs a fixed 12 weeks (matching `HORIZON_WEEKS`) and auto-cycles into a fresh one on expiry; a race-oriented one ends on `race_date`. The season also carries `anchor_weekly_volume_km` — the trailing weekly mean frozen at the moment the arc opened, which every prescription in it ramps off. `SeasonService::reanchorIfCollapsed()` is its only mid-season write: downward only, and only past a 25% collapse. See [[the-arc-is-anchored-once]]. Setting or clearing a `RaceGoal` mid-season closes the current season early (`ends_at` moves to the day before) and opens the other mode at the next call — never a gap, never an overlap, since the mode check always compares the CURRENT active race against the latest season's `race_goal_id`.

`SeasonGoal` rows generate at creation. A race season adds its block goals on the first call on or after block open, stamped as `seasons.block_goals_appended_at` so later calls skip the database. See [[gamification]] for the full list and the rest-day reward mechanism that isn't a `Badge`. A race season with fewer block rows from its start through race week than the full block serves a fixed under-ready line once on the Plan page, stamped as `seasons.under_ready_noted_at` ([SeasonService::takeUnderReadyLine()](app/Services/Run/Plan/SeasonService.php)); see [[the-block-opens-on-a-computed-date]].

### Season-wide summary — the nested timeline (`V0` fork 3, rebuilt by `PS4`)

`PlanController::index()`'s own `weeks` payload only ever covers a rolling `HISTORY_WEEKS`/`LOOKAHEAD_WEEKS` window (3 history + current + 4 lookahead), not the full season — real scope for a season-wide phase-progress bar and week-by-week volume timeline, deliberately left out of `S4` (see that slice doc's "Deliberately scoped OUT"). [SeasonSummaryBuilder::build()](app/Services/Run/Plan/SeasonSummaryBuilder.php) closes that gap with a separate, season-wide read model (`seasonSummary` Inertia prop): one entry per week from `Season::$starts_at` to `$ends_at`, each carrying its phase, its `general`/`block` zone, a `history`/`current`/`lookahead` type, a `planned_km` figure, a `sessions` count, and (once a [WeeklySnapshot](app/Models/WeeklySnapshot.php) exists for that week) an `actual_km`. The current week's `planned_km` has the km its recorded eases took off subtracted, with the forecast figure kept as `eased_from_km`, so the header agrees with the day rows beneath it ([[the-eased-session-leads]]). `SeasonSummaryBuilder::adherencePct()` is the season header card's headline figure — the mean of every persisted `compliance_score` inside the season, so it covers weeks the page no longer renders day rows for.

`planned_km` is computed the same deterministic, season-start-anchored way [SeasonService::generateGoals()](app/Services/Run/Plan/SeasonService.php) already sizes its `SeasonGoal` targets — `PhaseSchedule`/`WeekPlanBuilder`/`SegmentGenerator`, never a read of materialized `PlannedSession` rows. Those rows only cover the periodizer's own rolling `Periodizer::HORIZON_WEEKS` (12-week) horizon and get deleted/recreated on every weekly regeneration, so they're the wrong source for a stable, whole-season figure — the same reasoning that already keeps `SeasonGoal` targets off of them. The trade-off: a week's `planned_km` won't reflect a real-time adaptation (e.g. an in-week deload) the way the day-by-day schedule below it on the page does.

**Frontend**: `PS4` replaced fork 3's two flat panels (`SeasonPhaseBar`, `SeasonWeekTimeline`) and the flat day-card list beneath them with the prototype's single nested timeline (decision P22).

[SeasonHeaderCard](../../resources/js/components/plan/SeasonHeaderCard.tsx) heads the page: week X of N, the season adherence figure, the phase ribbon, one bar per phase (height by that phase's mean weekly volume, so the bar chart traces the season's real arc), the one-time under-ready line when the season payload carries one, and Temari's season narration. Its `phasesOf()` builds the bars from the phase sequence the season actually has, so a self-scaled season's repeating Build/Deload cycle renders honestly rather than being forced into a fixed Base/Build/Peak/Taper four (see `App\Enums\PlanPhase`'s own docblock on which phases exist in which mode).

**The phase ribbon** ([PhaseRibbon](../../resources/js/components/plan/PhaseRibbon.tsx)), bordered in `border-border` to hold its shape against either ground, is one cell per week of `seasonSummary`, season start to race day: a flat neutral "maintain" fill for every `zone: general` week regardless of its own `phase` (the self-scaled cycle alternates Build/Deload before the block opens, and showing that would read as noise), and a `PHASE_COLORS` fill per `zone: block` week. It reads `zone` off each week directly rather than the season payload's separate `block_opens_on` date — the per-week flag is already the boundary, so there's nothing left for a date comparison to add. No number ever appears in it: hovering, tapping or focusing a cell is the only way to see its phase name, which is also the cell's accessible name, and the current week is marked by drawing every week up to and including it solid, with every week still ahead faded (`opacity-40`) — the solid/faded edge is "now", not a separate ring or dot. A self-scaled season carries no `block` week at all, so it renders nothing. "Maintain" is a display label only: the season payload's own `zone` value stays `general`.

[SeasonTimeline](../../resources/js/components/plan/SeasonTimeline.tsx) is the rail beneath it. It splits the season into contiguous same-phase runs — not runs keyed on phase *name*, since a self-scaled season passes through Build more than once — shows the run holding the current week in full, and folds the weeks already behind in it, plus every later run, into a [WeekCluster](../../resources/js/components/plan/WeekCluster.tsx) summary row until asked for. Each [SeasonWeekRow](../../resources/js/components/plan/SeasonWeekRow.tsx) opens (the current week by default, every other week closed) onto a [WeekVolumeChart](../../resources/js/components/plan/WeekVolumeChart.tsx) — a dashed planned outline against a filled actual bar coloured by that day's compliance verdict — and a [WeekDayRow](../../resources/js/components/plan/WeekDayRow.tsx) per day. A week outside `PlanController`'s render window has no day rows to open and renders as a flat summary card instead.

**A week that is not an ordinary week says so in its header**, in words rather than in a bar colour: a `deload week` chip when the week's phase is `Deload`, and a `race week` chip on the week the goal race falls in. Both headers carry them, the collapsible one and the flat summary card. The race week is resolved client-side by [isRaceWeek](../../resources/js/lib/plan.ts) against the `race.race_date` the page already holds — the season summary spans weeks far past the periodizer's day-row horizon, which is exactly where a race sits, so a per-week server flag would be the wrong source. Deload's `stone` fill in [PHASE_COLORS](../../resources/js/lib/chartTokens.ts) still tones the volume chart; the chip is what makes the week legible without reading a legend.

A day row opens onto Temari's read on it, a [SessionBarGraph](../../resources/js/components/plan/SessionBarGraph.tsx) (the session's segments, width by minutes and height by zone, with interval repeats collapsed into one "N× Interval" legend block), a link to what was actually run, and the Move/Skip actions. Its collapsed state carries a [MiniSessionBar](../../resources/js/components/plan/MiniSessionBar.tsx) — the same zone strip at 4px.

Phase fill colors are the `PHASE_COLORS` export in [chartTokens.ts](../../resources/js/lib/chartTokens.ts), validated distinct via the dataviz skill's palette checker and deliberately drawn away from `PALETTE.overloaded`/`gassed`/`chill`, which are already committed to per-run Mood colors; zone fills reuse the existing `HR_ZONE_COLORS` ramp. Shared payload types, the adherence mean and the label maps live in [lib/plan.ts](../../resources/js/lib/plan.ts).

## Plan narration — voice only, layered on top

Two `AnalysisType` cases narrate what the rules above already decided, never re-deciding it: `PlanDayVoice`, `PlanSeasonVoice`. Both follow the standard AI narration pipeline (see the "AI narration pipeline" section of CLAUDE.md) — `PlanDayVoiceNarrator`/`PlanSeasonVoiceNarrator` under [app/Services/AI/Narrators/](app/Services/AI/Narrators/), one `AnalyzeRowJob` subclass each under [app/Jobs/AI/](app/Jobs/AI/).

**The week's own adaptation display never went through narration.** The headline, detail sentence
and deload/quality chips `SeasonWeekRow` and `SeasonHeaderCard` show for the current week come
straight off the periodizer's own [`PlanAdaptation`](app/Models/PlanAdaptation.php) row and
[`AdaptationReason::headline()`/`::detail()`](app/Enums/AdaptationReason.php) — deterministic, not
LLM voice. A `plan_week_voice` narrated line used to sit alongside it as `SeasonWeekRow`'s
collapsed "Temari's take"; the owner cut it 2026-09-17 (#947) since it added no information the
deterministic display didn't already carry. See [[llm-triggers]]'s Retired surfaces for what
removing the `AnalysisType` case did to existing `plan_week_voice` rows.

**Day narration is a read, requested only once a day has a run — never ahead of time** (#939). A day
not yet run, a missed day, or an excused day shows no `plan_day_voice` block and asks for no LLM
call; a rest day run anyway still has a run, so it still gets one. `PlanDayVoice`'s subject is a
synthetic `user_id` + `Y-m-d` discriminator key (mirroring `BriefingMascotVoice`'s own per-user-per-day
shape), not the `PlannedSession` row's own id — that row's id is *not* stable across weekly
regenerations (`Periodizer::regenerate()` deletes and recreates every unpinned future-date row), so
keying on it would silently orphan a day's narration history every Monday even when the actual
prescribed session never changed. Editing a day (`PlanController::update()`, skip or move) re-requests
that day's narration only when the touched day is already credited — an edit almost always touches a
day still ahead, which has no read to keep in sync in the first place.

**Season narration attaches to `Season`**, requested on every dispatch. Almost everything about a season's material is fixed at creation (a mode switch opens a new `Season` row rather than mutating this one), so an already-`Done` row is normally left alone on `AnalysisService`'s own idempotency alone, with no explicit "did the season actually change" check. The one exception is [SustainedAheadOfRacePace](app/Services/Run/Plan/SustainedAheadOfRacePace.php) (#933): whether the athlete has held [AdaptationReason::AheadOfRacePace](app/Enums/AdaptationReason.php) for two consecutive evaluated weeks is genuinely time-varying on an otherwise-unchanged season row, so [PlanNarrationRequester::requestWeek()](app/Services/AI/PlanNarrationRequester.php) folds it into [MaterialFingerprint::forSeason()](app/Services/AI/MaterialFingerprint.php) and invalidates explicitly when the stamped fingerprint no longer matches — a never-fingerprinted `Done` row (any season narrated before this signal existed) reads as changed, so every season re-narrates once rather than silently never mentioning a goal already held for weeks.

**A day's read re-bills only where the verdict actually changed.** It is requested from exactly one
site — [DispatchPostRunAnalysis](app/Listeners/DispatchPostRunAnalysis.php) calling
[`requestDayVoiceIfChanged()`](app/Services/AI/PlanNarrationRequester.php) right after
`ComplianceScorer::creditIfEarned()` credits today's run — never from the Monday sweep or a
regenerate, which touch only the season. Each row is stamped with a
[MaterialFingerprint](app/Services/AI/MaterialFingerprint.php) of what it describes
(`forPlannedSession()` mirrors what [PlanDayTool](app/Services/AI/Agent/Tools/PlanDayTool.php) hands
the model, including the intent verdict), written by the job through `AnalyzeRowJob::fingerprintFor()`,
and [PlanNarrationRequester](app/Services/AI/PlanNarrationRequester.php) invalidates a row only when
the fingerprint no longer matches — so a second run the same day that does not move the verdict
re-bills nothing. A manual edit through `PlanController::update()` still re-narrates unconditionally
once the day is credited, since the athlete just changed that day on purpose.

**Past days of the current season get the same read, rule-based, in one deploy-time step.**
`plan:regrade-season` ([RegradeSeasonCommand](app/Console/Commands/Run/RegradeSeasonCommand.php))
backfills a `plan_day_voice` row for every credited day it regrades via
[`PlanNarrationRequester::backfillRuleBasedRead()`](app/Services/AI/PlanNarrationRequester.php),
phrasing the same verdict [RuleBasedNarrationFiller::planDayVoice()](app/Services/AI/RuleBased/RuleBasedNarrationFiller.php)
uses for the demo account — never the LLM, and idempotent to re-run. The demo account's own Plan
page fills a credited day's read the same rule-based way, through
`PlanNarrationRequester::ensureDemoFilled()`, the path its manual "Reread" already resolves through.

**Season narration is dispatched from `Periodizer::regenerate()`'s two callers, never from `Periodizer.php` itself** — [PlanController::regenerate()](app/Http/Controllers/PlanController.php) (manual) and [RegeneratePlanCommand](app/Console/Commands/Run/RegeneratePlanCommand.php) (the weekly cron), via [PlanNarrationRequester](app/Services/AI/PlanNarrationRequester.php). Literally dispatching narration inside `Periodizer.php` would contradict its own "no LLM call anywhere in this feature" heritage; keeping the requester one layer up preserves that boundary while still tying narration to the exact moment the underlying facts change. `RegeneratePlanCommand` narrates the season of every athlete [RecentlyActiveUsers](app/Actions/AI/RecentlyActiveUsers.php) returns — demo excluded, and only someone who opened the app inside the active window ([[narration-follows-the-athlete-not-the-run]]) — while the regenerate half stays exactly as free as before and still runs for everyone. The narration half is real per-user LLM cost, so it's classified `BILLING` in [DemoBillingExclusionTest](tests/Feature/Console/DemoBillingExclusionTest.php) even though the command's own regenerate call is unconditional.

**The manual Regenerate button still carries a real rate limit.** A full regenerate dispatches the season narration row — real LLM cost per click — so `PlanController::regenerate()` checks a dedicated one-hour cooldown (`PlanNarrationRequester::regenerateCooldownRemaining()`/`startRegenerateCooldown()`) before calling the periodizer, started immediately rather than waiting for the async narration job to finish (closing the queue-latency window where two rapid clicks could both slip through). It's a standalone `Cooldown` key, not `Analysis::cooldownKey()` reused — every narration row's own completion unconditionally starts its own shorter (15-minute) cooldown in `AnalysisService::markDone()`, so sharing the key would have this longer window silently overwritten within moments. The weekly cron starts the same cooldown after its own regenerate (so a manual click right after Monday's auto-run is still correctly rate-limited) but never checks it — the cron always runs.

### No season track on the page

`PP3` cut the `SeasonTrack` tier module (P24): the prototype's Plan screen draws a
`SeasonHeaderCard` with a single progress line, not a pip rail. The season-scoped reward engine
behind it — `GrantSeasonUnlocksAction`, the `season.{id}.track_{N}` grants and the
`season.tiers_kept_from_past_seasons` count — went with the rest of the unlock system, since
nothing had rendered any of it since P24. What remains is the `SeasonGoal` set itself, resolved
live by [SeasonGoalResolver](../../app/Services/Gamification/SeasonGoalResolver.php) and drawn as
that single progress line.

The per-goal `GoalCard` grid under the season summary is gone: P24 replaced the tier module with
the prototype's single progress line, and `W2` swept the orphaned component. The week-grained
lifetime streak
(`WeeklySnapshot::consecutiveWeekStreak()`, wrapped by `SeasonStreakSummaryBuilder::streakPayload()`)
does not render here either — it lives on Trends as a badge chip. `PlanController` still calls
`seasonPayload()`, never `streakPayload()`.
