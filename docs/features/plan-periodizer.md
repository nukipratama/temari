# Plan — deterministic periodizer and the Plan tab

The training instrument's forward half: a rules-only periodizer that fills a per-day plan (`planned_sessions`), rendered on its own top-level `/plan` tab. **Rules own every number, the LLM owns voice only** (see the "Plan authorship" row in the v2 program's locked decisions) — every figure in this doc through "Season" below is deterministic; the one LLM layer, "Plan narration" at the end, only narrates verdicts the rules already reached and never computes anything itself.

## Two seams: one assembler for the page, pure inputs for the periodizer

Nothing outside `App\Services\Run\Plan` assembles the plan itself. Two entry points stand between the engine and its callers:

- **The page.** [PlanPageAssembler](app/Services/Run/Plan/PlanPageAssembler.php) owns every prop `/plan` renders — race, baseline session count, the multi-week arc with the readiness clamp and volume redistribution applied ([::weeks()](app/Services/Run/Plan/PlanPageAssembler.php)), the season trio, the adaptation explanation and the narration payloads. [PlanController::index()](app/Http/Controllers/PlanController.php) decides only which of them Inertia defers. The assembler is bound `scoped()` because Inertia's partial reload runs the action a second time and three props want the same ensured season. Until then the controller reached for eleven `Run\Plan` primitives directly, the only consumer outside the namespace to do so.
- **The plan.** [PlanInputs](app/Services/Run/Plan/PlanInputs.php) is the whole database read a regeneration needs — season window, active race and its projection, stated preferences, behavioral session count, the days the athlete pinned or already ran, and the adapter's verdict — gathered by [PlanInputsGatherer::forUser()](app/Services/Run/Plan/PlanInputsGatherer.php). [Periodizer::rowsFor()](app/Services/Run/Plan/Periodizer.php) turns those inputs into a row per calendar day and touches neither the database nor the clock; [::regenerate()](app/Services/Run/Plan/Periodizer.php) is gather-then-persist over it. The arc's ramp, deload, taper and peak behaviour is therefore asserted against hand-built inputs in `tests/Unit/Services/Run/Plan/PlanInputsTest.php`, with the feature suite left to prove what only persistence can — that the season stays anchored across successive Mondays.

## Shown recommendation history

[RecommendationHistory](app/Services/Run/Plan/RecommendationHistory.php) preserves the original and effective workout, segments, pace inputs and policy version independently of mutable daily-row IDs. Rendering returns an encrypted snapshot without writing history for every fetched future row. [useRecommendationView](resources/js/hooks/useRecommendationView.ts) acknowledges only the intersecting Today or selected Plan panel while the document is visible; no Start or accept action is required. The authenticated endpoint checks snapshot ownership. A receipt UUID makes retries idempotent, and immutable view rows retain the server acknowledgement time in UTC.

[ComplianceScorer](app/Services/Run/Plan/ComplianceScorer.php) reads the last acknowledged recommendation strictly before the activity's UTC start, using the day's longest activity as its grading anchor. It retains the displayed distance, segments and pace inputs rather than recomputing them from later fitness. Multiple activities still follow the existing daily credit rules. Ingest stores Strava's UTC start separately from its local calendar date. Activities without a reliable UTC start or prior acknowledgement are graded `unknown` with `advice_history: unknown`: distance credit and actual load stand, intent is never reconstructed, and the row never teaches quality progression. This layer does not fabricate historical views or mass-regrade existing records. The scorer keeps three things apart on `planned_sessions.intent_evidence`: the original session, the effective advice shown (`effective_type`, `eased_from`, and a `concern` of `none`, `mild` or `strong` read from the shown readiness assessment, strong only for a rest or easy-only ceiling on severe fatigue, concerning pain or illness) and the stimulus actually done (`stimulus_family`, `stimulus_minutes`, `stimulus_source`, summed over the day's runs). A controlled original quality session completed against mild eased advice carries `original_completed` and reads as completed but past the recovery advice; hard work on an easy day reads as an unplanned hard effort. A row stamped `quality_progression: eligible` (shown, unchanged quality advice, a `hit`, `missed` or `too_hard` verdict) is the only kind that teaches progression or stimulus adherence. Race confirmation is a separate layer of the coaching redesign. See [[grading-follows-shown-advice-and-actual-stimulus]].

Calendar matching keeps the current app timezone and Strava local date compatibility. Midnight and travel can therefore cross calendar boundaries; UTC is used for ordering only. A failed or delayed acknowledgement is conservative: advice is unknown if the server cannot establish that it was seen before the run. Dropping the history migration loses this evidence and returns grading to `unknown` intent, so rollback requires preserving/exporting the ledger first.

## Two modes, chosen fresh on every regeneration

[Periodizer::regenerate()](app/Services/Run/Plan/Periodizer.php) reads the user's active [[race-projection|race]] through [ResolveActiveRaceAction](app/Actions/Run/Plan/ResolveActiveRaceAction.php) — a `scoped()` memo, so the plan engine, the season service and the page's own controller share one read per request — and picks a mode. A mode switch (setting or clearing a race) takes effect at the *next* regeneration, never retroactively.

- **Race-oriented** ([PhaseSchedule::forRace()](app/Services/Run/Plan/PhaseSchedule.php)): **the race block is bounded by distance.** The block is 16 weeks ending on race week up to the half marathon, and 20 weeks past it, so `PhaseSchedule::blockOpensOn()` returns race week's Monday minus 15 or 19 weeks. Weeks from the season's start to block open run the self-scaled cycle below (`zone: general`), and only the weeks from block open to race day are periodized (`zone: block`). A block opening on or before the season's start covers the whole span. Block open is a computed date, never a season boundary. See [[the-block-opens-on-a-computed-date]]. A general cycle that would reach block open two or more weeks past its last recovery week ends on one instead ([PhaseSchedule::generalCycleUntil()](app/Services/Run/Plan/PhaseSchedule.php)), so the seam never runs more than four weeks without a dip while the block keeps the cadence it has standing alone. Inside the block, every race up to 25&nbsp;km tapers for 2 weeks and a longer one for 3 ([[a-race-block-tapers-two-weeks-and-recovers-in-peak]]). The block and its marathon-class work end at the marathon: a race beyond 42.195&nbsp;km has no block and runs the self-scaled cycle through race week with one taper week, a long-run cap at the general aerobic ceiling and no race-specific quality ([[road-preparation-ends-at-the-marathon]]). Too little time to build anything (`weeksToRace &le; taperWeeks + 1`) skips straight to a taper-only arc. Otherwise the weeks remaining after the taper split `base 30% / build 45% / peak 25%` (peak and build each floored at 1 week, base absorbs the remainder so the three always sum exactly — no rounding drift). Build ramps volume ~7.5%/week compounding, **capped so no multiplier passes 1.4** (a 12-week block's 1.24 and a 16-week block's 1.34 are untouched; a 20-week block is trimmed from 1.44, and a 52-week arc no longer reaches 3.42) — see [[a-goalless-arc-does-not-ramp]]; Peak holds build's final multiplier, so the long run climbs or holds until the taper; Taper reduces from it along a `-20% / -40% / -60%` curve (the nearest-to-race week always lands on the steepest cut, scaled for shorter tapers) — see [PhaseSchedule::volumeMultipliers()](app/Services/Run/Plan/PhaseSchedule.php). **Every fourth week of the base/build/peak stretch is a scheduled recovery week**, so the ramp never compounds unbroken (five build weeks would otherwise be +33% with nothing absorbing it); Taper is exempt, a stretch shorter than four weeks gets none, one that would land on the last week before Taper moves a week earlier so Taper always follows a Peak week, a recovery week inside Peak dips off the build level and Peak returns to it after, and the ramp *resumes* from the level it reached rather than restarting after the dip ([[a-race-block-never-prescribes-below-habit]], [[a-race-block-tapers-two-weeks-and-recovers-in-peak]]). A week resumed after a postponement or target change is also bounded by [Periodizer::boundResumedWeek()](app/Services/Run/Plan/Periodizer.php): while a revision from the last four weeks stands, the planned volume never exceeds 1.1&times; the trailing four-week mean of actual weekly km (no clamp under two weeks of history), and each later week rises by at most 1.1&times; until the arc's own value is reached. A resumed Deload week under the ceiling carries that ceiling to the following week, so the week after a recovery week stays under it rather than jumping to the arc ([[a-race-event-keeps-its-season]]). Until [[the-plan-follows-the-coaching]] the only deload here was the reactive one below, which fires after readiness or adherence has already slipped.
- **Self-scaled** ([PhaseSchedule::selfScaled()](app/Services/Run/Plan/PhaseSchedule.php)): no taper/peak exists without a race date to count back from, so it cycles a repeating 3-weeks-build : 1-week-deload mesocycle indefinitely, **holding flat at 1.0 with its deload weeks at 0.65** rather than ramping, since a ramp on top of a trailing-volume baseline counted the same growth twice and prescribed 2.75x actual volume at 20 weeks. The long-run baseline is solved so the four-week cycle averages the season's frozen anchor, unless a long-run cap binds ([[a-season-averages-its-anchor-and-no-session-outruns-recent-capacity]]). The solve sizes the cycle under `long_run_cap_km` and the progression cap, so sessions under their cap carry what a capped one loses ([[a-goal-less-cycle-solves-under-the-session-caps]]). `volumeMultipliers()` takes the mode explicitly, since a phase sequence alone cannot say which produced it. See [[a-goalless-arc-does-not-ramp]]. **Post-race recovery is derived on every regeneration, on whichever arc follows.** [PlanInputsGatherer::postRaceRecovery()](app/Services/Run/Plan/PlanInputsGatherer.php) takes the latest race in the past 14 days with known load: a confirmed outcome, or an owned race-day run matching the event. A did-not-run or cancelled answer always wins over a matching run. [PostRaceRecovery::after()](app/Services/Run/Plan/PostRaceRecovery.php) sizes the window by the distance actually run: 30 km or more gets 14 days with no quality plus the first full Monday-start week after race day at the deload multiplier; over 15 km gets 7 days with no quality at normal volume; 15 km or less gets 3 days with no quality. [Periodizer](app/Services/Run/Plan/Periodizer.php) turns quality inside the window into an easy day and [applies the deload week](app/Services/Run/Plan/Periodizer.php), so a race block opening inside the window starts with it. Recording an outcome regenerates the plan ([RaceOutcomeService](app/Services/Run/Plan/RaceOutcomeService.php)), so a late confirmation reaches it. See [[post-race-recovery-follows-known-race-load]].

Both modes materialize up to `Periodizer::HORIZON_WEEKS` (12) weeks of rows; a race-oriented arc that resolves to fewer weeks simply writes fewer. A race arc ends with race *week*, not race day.

**The arc is counted from the season, then sliced** ([Periodizer::sliceFromCurrentWeek()](app/Services/Run/Plan/Periodizer.php)). Both modes build the whole arc from the `Season`'s own start week and compute `volumeMultipliers()` across all of it *before* taking the horizon's worth that starts at the current week. Counting the arc from "today" instead put the week actually being trained at index 0 every Monday, which is `1.0` in every phase but Taper — so Build, Peak and the scheduled Deload were only ever visible in the lookahead. The multiplier that survives the slice is stamped on each row (`planned_sessions.volume_multiplier`) rather than recomputed at render, because a render window reaching back three weeks cannot see where the season began. See [[the-arc-is-anchored-once]].

**Race week is shaped around the race.** [WeekPlanBuilder::raceWeekType()](app/Services/Run/Plan/WeekPlanBuilder.php) overrides the day template for the week the goal race falls in: race day is a [SessionType::Race](app/Enums/SessionType.php), the day before it is rest, and so is every day after it. Until [[the-plan-knows-its-race-day]] the race date reached [PhaseSchedule::forRace()](app/Services/Run/Plan/PhaseSchedule.php) and nowhere else, so race week was laid out as an ordinary tapered week — a Sunday marathon got a long run the day before it and `rest` on the day itself, and a Tuesday 10K got a tempo session ON the race. **Race day is prescribed at the athlete's own goal**: [SegmentGenerator::raceSegments()](app/Services/Run/Plan/SegmentGenerator.php) divides `goal_time_sec` by the race distance, so a 59:00 10K reads 5:54/km rather than the 5:44/km threshold band the pace zone alone would give. The band survives as the qualitative zone label. With no goal time behind the row — a past race, once `plan:close-finished-races` has retired the goal — the band's own pace stands in.

A `Race` row carries its own `race_distance_m` ([PlannedSession](app/Models/PlannedSession.php)) rather than reading the goal back at render time: `plan:close-finished-races` retires the `RaceGoal` at 00:04, *before* `plan:score-compliance` grades the day, so the goal is already gone by the time anything needs the distance. That distance is what [SegmentGenerator::coreKmFor()](app/Services/Run/Plan/SegmentGenerator.php) sizes the day from — the one session sized from outside the athlete's own training, and the one the volume redistributor never scales. A race goal or pinned prescription does not establish readiness: its stored workout stays fixed, while today's safety advice may still show beside it. Manually moving a Race workout transfers its stored distance with the workout; the calendar date changes, but the canonical RaceGoal.race_date does not.

## Shared session-structure logic

[TrainingBaseline](app/Services/Run/Plan/TrainingBaseline.php) reads the athlete's own recent behavior fresh on every call (never frozen): sessions/week from the trailing 6-week average run count (clamped 3-6), weekly volume from a **trimmed mean** of those six weeks (highest and lowest dropped), and the long run derived as a share of that volume — floored three ways in a race season, and capped by a race-distance band, by 150 minutes of easy running and by half the anchor week's volume, whichever binds first; that cap bounds the long run against the anchor, not against the week it is prescribed in, so a two-run week can still give the long run more than half its km. **The long-run floors are a starting point, not a jump** ([TrainingBaseline::longRunTargetFloorKm()](app/Services/Run/Plan/TrainingBaseline.php)): the block's target long run (the race distance below the marathon threshold, and the readiness distance for every race: 12 km for a 10K, 18 km for a half, 30 km for a marathon, bounded by the cap) is divided by the biggest **Build or Peak** multiplier the block reaches, so the athlete arrives there by running the ramp. Taper and Deload multipliers are reductions and never count; a block holding neither Build nor Peak gets no floor. **The volume floor** ([TrainingBaseline::volumeFloorKm()](app/Services/Run/Plan/TrainingBaseline.php)) lifts the baseline until the block's weeks, laid out with the same projected race time, fall-off tilt, run days and two-run quality eligibility [Periodizer](app/Services/Run/Plan/Periodizer.php) lays them out with ([TrainingBaseline::weekLayout()](app/Services/Run/Plan/TrainingBaseline.php)) and sized under `long_run_cap_km` and the progression cap below, average the season's frozen `volume_floor_km`, the athlete's plain twelve-week actual mean at season start, or come as close as those caps allow; the half-the-anchor cap is sized off the bigger of that and the anchor. A race season opened while a run inside the load guard's 42-day window still awaits hydration is stamped `increases_held`: its block runs flat, with no ramp and no long-run target floor, and its training weeks average the floor, each within 10% of it, until a regeneration finds that load scored. Time-trial weeks and the taper quality days the intensity step eases, by the minimum-quality fit or the hard-minute ceiling, stay out of the solve, so those weeks may render under it; every other block week renders the km the solve lays out. See [[a-race-block-never-prescribes-below-habit]], [[the-volume-floor-solves-the-weeks-the-plan-lays-out]] and [[trial-weeks-and-eased-taper-days-sit-outside-the-floor]]. **Those ceilings bind on the prescription too, not only on the baseline.** `forUser()` returns the tighter of the three as `long_run_cap_km`, and [SegmentGenerator::coreKmFor()](app/Services/Run/Plan/SegmentGenerator.php) bounds `baseline * multiplier` by it — the single point every session type is a fraction of. Applying them to the baseline alone let the volume multiplier walk straight through: a 52-week-out 10K prescribed a 31.1 km long run and a 20.2 km tempo. A separate `long_run_progression_cap_km` holds every planned running session to 110% of the longest completed run in the prior thirty days, and with no run in that window it is the cold-start long run ([[recent-single-run-cap-stages-long-run-progression]], [[a-season-averages-its-anchor-and-no-session-outruns-recent-capacity]]). The baseline is deliberately *not* the longest recent run: that let one outlier set every session in the week, since [SegmentGenerator::coreKmFor()](app/Services/Run/Plan/SegmentGenerator.php) scales the whole week off this one scalar. See [[plan-volume-anchors-on-weekly-mean]]. An explicit [TrainingPreference](app/Models/TrainingPreference.php) row sits above that behavioral read, not beside it: a set `sessions_per_week` always overrides the behavioral average (bypassing its 3-6 clamp — 2 is a valid explicit choice, just not a valid *inferred* one), and with zero logged weeks *and* no explicit `sessions_per_week`, a stated `experience_level` seeds which cold-start `[sessions, km]` pair to use instead of one flat default for every brand-new athlete. Real logged behavior always wins the moment any exists, regardless of what was once claimed. `TrainingPreference.goal_type` carries no computational weight in this class or anywhere else in the periodizer — it's narration-flavor signal only, since `RaceGoal`'s presence/absence already fully selects the periodization mode below.

[WeekPlanBuilder](app/Services/Run/Plan/WeekPlanBuilder.php) fills only selected weekdays, or its existing 2–6-run templates when no weekdays were selected. Two runs start Easy plus Easy Long. Credible guide paces and six recent completed weeks with at least two actual runs each permit a controlled Tempo in Base/Build/Peak, capped at ten hard minutes; Deload/Taper retain the easy foundation, and two-run Long work never gains race-pace intensity. This is a conservative eligibility heuristic, not a research-derived threshold. Beginners and insufficient-history athletes retain the foundation, and the whole-week time reserve and meaningful segment fit can still remove quality. Three or more runs retain the phase and projected-race-duration rules, with at most two demanding days. Rest and ordinary Easy days both provide recovery; unavailable weekdays are never added to fit quality.

**The athlete's own fall-off tilts a race block's mix** ([FallOffTilt](app/Enums/FallOffTilt.php)). [TrainingBaseline::weekLayout()](app/Services/Run/Plan/TrainingBaseline.php) reads the fall-off k and whether it was fitted from the supported-time estimate ([[supported-race-time-from-recent-efforts]]). Only a fitted k counts, so a default k never tilts. A fitted k at `FallOffExponent::MIN` (a raw fit of 1.06 or less) tilts toward speed, one above 1.10 toward endurance, and the band between is neutral. The tilt applies only in Build and Peak weeks of a race block; Base, general-zone, Deload, Taper and self-scaled weeks and the marathon-distance race-pace slot are untouched. It moves only a quality slot the race duration leaves open ([WeekPlanBuilder::tiltedSingleSlot()](app/Services/Run/Plan/WeekPlanBuilder.php), [tiltedPair()](app/Services/Run/Plan/WeekPlanBuilder.php)): a single quality day for a race projected between the VO2max and threshold durations goes Tempo for endurance or Interval for speed in either phase, and a two-slot week turns its Tempo + Interval pair into two of the tilt's type unless a race under the VO2max duration keeps its Interval or one at or over the threshold duration keeps its Tempo. The hard-day budget, the quality-delta drop and volume are unchanged: the volume-floor solve lays the tilted weeks out, so the other sessions absorb the longer quality day and long run. The endurance tilt also lengthens the Build and Peak long run by `FallOffTilt::ENDURANCE_LONG_RUN_FACTOR` (10%), still under `long_run_cap_km` and the 30-day progression cap ([SegmentGenerator::coreKmFor()](app/Services/Run/Plan/SegmentGenerator.php)). Generation stamps which tilt shaped a row in `planned_sessions.fall_off_tilt`, cleared when the week then keeps that day easy. Long runs are sized at read time from that stamp, so a past week and `plan:regrade-season` read the same km whatever the current fit. There is no hysteresis: a refit across a band flips the tilt at the next regeneration, with no notification, and k is never shown. [DayDetail](resources/js/components/plan/DayDetail.tsx) ends "the point" with one italic line on a session the tilt moved, while that session is shown as written ([PlanRenderer::shownFallOffTilt()](app/Services/Run/Plan/PlanRenderer.php)); a tilted long run the caps held to its untilted length shows none.

**The last weeks rehearse the goal pace** ([GoalPaceWork](app/Services/Run/Plan/GoalPaceWork.php), [[goal-pace-work-in-the-last-weeks]]). Counted back from race week, inclusive, the last 6 weeks before a race up to 10K and the last 8 before a longer road race are the window. Inside it, only Build, Peak and Taper weeks of an `on_track` or `ambitious` goal ([PlanInputsGatherer](app/Services/Run/Plan/PlanInputsGatherer.php) reads the band) turn one session into goal-pace work, at the real goal pace, and those of an `unsupported` goal at its stepping-stone pace, the supported time × 0.97 ([PlanInputsGatherer](app/Services/Run/Plan/PlanInputsGatherer.php), [[a-stepping-stone-for-an-unsupported-goal]]). [Periodizer](app/Services/Run/Plan/Periodizer.php) picks it ([GoalPaceWork::replacedDate()](app/Services/Run/Plan/GoalPaceWork.php)): the Interval for a 5K or 10K, the Tempo for the half and the marathon, otherwise the week's first Tempo or Interval. The work keeps the kind's shape whatever the day's type, reps for 5K and 10K and a block for the half and the marathon ([GoalPaceWork::shapeOf()](app/Services/Run/Plan/GoalPaceWork.php)), so a replaced session never adds a hard day. The dose comes from `GOAL_PACE_TARGETS` by kind and phase, halved for an ambitious goal and full for an unsupported one ([IntensityPrescriptionResolver](app/Services/Run/Plan/IntensityPrescriptionResolver.php)); the marathon keeps `RACE_TEMPO_TARGETS`, and an on-track marathon's race long runs its marathon-pace block at goal pace, an unsupported one's at the stepping-stone pace. These numbers are a **heuristic**. Progression reads its own `goal_pace` family for 5K to half. A dose too big for the day's distance steps down by whole work units before the day goes easy ([Periodizer](app/Services/Run/Plan/Periodizer.php)). `low_evidence` and `unknown` goals get no goal-pace work, nor does a goal more than 3% slower than the supported time, and the marathon keeps its clamped race Tempo and race Long for them. The band, goal pace and kind are stamped in `prescription_race_context`, so the "goal pace" label on Home, the day detail and the week strip ([PlanRenderer::goalPaceKindOf()](app/Services/Run/Plan/PlanRenderer.php)), or "stepping-stone pace" for an unsupported goal ([GoalPaceWork::isSteppingStone()](app/Services/Run/Plan/GoalPaceWork.php)), and intent grading read what generation decided.

**A time trial checks fitness about every six weeks** ([TimeTrialSchedule](app/Services/Run/Plan/TimeTrialSchedule.php), [[a-time-trial-every-six-weeks]]). The trial is 5K, or 10K for a half marathon or longer goal ([TimeTrial::distanceFor()](app/Services/Run/Plan/TimeTrial.php)). A race season counts back from race week: the last trial 4 weeks before it, then every 6 weeks earlier; a season with no race starts in its third week, then every 6 weeks. A trial due in a scheduled Deload week falls due the week before it, which puts a full block's last trial 5 weeks out ([[a-race-block-tapers-two-weeks-and-recovers-in-peak]]). No trial falls in the last 3 weeks before a race. The 6-week cadence, the 3-week exclusion and the 4-week recent-evidence skip are **heuristics**. Confirmed evidence or a hard effort within ±10% of the trial distance from 4 weeks before the due week skips that cycle. [Periodizer](app/Services/Run/Plan/Periodizer.php) puts the trial in the week's first Tempo or Interval still prescribed as quality, so the hard-day count is unchanged; the hard-minute ceiling shrinks the other sessions instead of the trial, and the hard-day spacing keeps the trial first. A week that cannot hold it (deload, no quality slot, or spacing that drops it) moves it to the next week of its cycle, and in a goal-pace week the trial takes the goal-pace session and the week has no goal-pace work. The day is sized like race day, the trial distance alone at the aim, the supported time at that distance, with no warmup carved into its distance or bar graph ([TimeTrial::dayKm()](app/Services/Run/Plan/TimeTrial.php), [PlanInputsGatherer](app/Services/Run/Plan/PlanInputsGatherer.php)), stamped with the distance, aim and retry flag in `prescription_race_context`, and kept out of every progression family. [PlanInputsGatherer](app/Services/Run/Plan/PlanInputsGatherer.php) reads the season's fixed trials and marks each skipped when the athlete excused it, nothing ran on its day, or readiness eased it to easy; a skipped first trial is offered once more in the following week's first quality slot, never in a deload week or the last 3 weeks before a race. The trial day is credited on its whole-day distance, capped at the trial distance so a warmup never reads as overreaching, and its intent is the gate ([[a-time-trial-every-six-weeks]] decision 11). The day carries one hint: warm up first as before a race, and record the trial as its own run if you can. Once the day is over, `plan:settle-time-trials` ([TimeTrialService::settle()](app/Services/Run/Plan/TimeTrialService.php)) writes `Test` evidence for a run within ±10% of the distance, or for the best split at the trial distance of a longer run ([TimeTrial::reading()](app/Services/Run/Plan/TimeTrial.php), a **heuristic** exception to the whole-run rule for planned trial days only), and no slower than the aim plus 5% (a **heuristic**) or averaging heart-rate zone 4 or above, and otherwise asks once on the inbox, by push and on Home. A trial whose run is still only a summary is left unsettled for a later run of the command within its seven-day lookback. Deleting that run on Strava, or re-typing it to another sport, retracts its `Test` evidence and regenerates the plan if the training paces moved, while a race result the athlete confirmed stays ([DeleteIngestedRunAction](app/Actions/Run/DeleteIngestedRunAction.php)). Home, the day detail, the week strip and the bar graph label the day "time trial" ([PlanRenderer::timeTrialOf()](app/Services/Run/Plan/PlanRenderer.php)).

[Periodizer](app/Services/Run/Plan/Periodizer.php) allocates complete weeks using actual performed duration and credible HR Z3–Z5 or threshold lap/GAP minutes, retained future prescriptions and generated work. Multiple activities on one date are combined, with actual execution replacing that date's original prescription rather than counting both. Skips, missed rows and unperformed past prescriptions spend no budget. A credited day budgets as the session it effectively was ([EffectiveSession::budgetProfileOf()](app/Services/Run/Plan/EffectiveSession.php)): an eased Tempo spends none of the abandoned Tempo's hard minutes, while self-added hard work, or a quality session completed against eased advice, counts as a demanding day with its measured minutes. A completed Race with unknown effort reserves a demanding day; credible actual execution determines measured intensity, race-pace Long spends quality budget, and an Easy Long keeps its recovery spacing without spending a quality place. Absolute calendar dates protect adjacent days around previous-week actual demands, pinned future work across the next boundary and already generated weeks; impossible clusters lose quality. Known demanding work with unknown hard minutes conservatively withholds additional quality without inventing measured minutes. Today’s adapter quality change applies only to the current week. When actual workload changes but adaptation does not, reconciliation reduces only affected unpinned current-week prescriptions, retaining other rows and existing clamps. See [[the-plan-follows-the-coaching]].

[IntensityPrescriptionResolver](app/Services/Run/Plan/IntensityPrescriptionResolver.php) resolves the quality dose before segments are drawn. The row stores its hard minutes, pace band, resolved pace, race context and deterministic reason, so later rendering and grading read the coaching decision that was actually made rather than silently recomputing it from newer fitness. Phase targets are ceilings, not automatic doses: sparse history starts conservatively, a recent comparable `hit` progresses, `too_hard` steps down, and `missed`/`unknown` hold, but only from rows the scorer marked `quality_progression: eligible`. Missing or unknown history, an eased session completed easy, and self-added hard work on an easy day cannot step a prescription up or down. These historical verdicts stay stored, while measured distance remains independently credited. The weekly allocator also reserves at least 70% Easy time and at most two hard days; when that reserve binds, the largest hard contribution gives way first.

[SegmentGenerator::forPrescription()](app/Services/Run/Plan/SegmentGenerator.php) lays that stored decision into the day's full ordered [SessionSegment](app/Services/Run/Plan/SessionSegment.php) list. The headline `distance_km` remains the whole outing: warmup, recovery, hard work and an explicit `easy` remainder add back to it, while a day too short for meaningful quality becomes one Easy block. Tempo keeps its phase-shaped blocks and Interval keeps whole repetitions. Marathon/ultra Long work is Easy opening, one late race-specific block, then a short Easy finish. **A cooldown is still never prescribed.** Without VDOT, the hard-day and phase caps still apply, but no invented weekly percentage or displayed pace target is created; segment distances remain unmeasured until a reliable sizing pace exists. See [[a-session-is-the-whole-outing]] and [[plan-recalibration-rewrites-history]]. **Each block carries one guide pace from the athlete's own VDOT race model** ([TrainingPaceCalculator::fromVdot()](app/Services/Run/Metrics/TrainingPaceCalculator.php)): marathon at the marathon race equivalent, threshold at the pace they could race for an hour, interval at about eleven-minute race pace, easy at the midpoint of the VDOT calculator's E band. See [[guide-paces-follow-the-vdot-race-equivalents]] and [[coaching-evidence]].

## Editable, pinned, regenerated

[EffectiveSession](app/Services/Run/Plan/EffectiveSession.php) composes a recorded modern readiness dose with the current base prescription: the stricter known hard-minute and pace limits win, the known current band/context sets the composed intensity, and a new Easy/zero-hard prescription removes saved quality. Both same-week reconciliation and full regeneration preserve the assessment/history without letting an old adjustment exceed a tighter workload cap. Recorded distance remains authoritative for modern and legacy rows; reconstructing a smaller core distance does not retrospectively change shown or graded volume. Rest and pace-clamp precedence remain unchanged.

**Which edits a day takes is decided in one place**, [SessionEditRules](app/Services/Run/Plan/SessionEditRules.php). [PlanController::update()](app/Http/Controllers/PlanController.php) checks it under the plan lock, and [PlanPageAssembler](app/Services/Run/Plan/PlanPageAssembler.php) ships its answer as each day's `actions` and `move_targets`, which [DayDetail](resources/js/components/plan/DayDetail.tsx) reads rather than deciding from dates. Today and every day ahead take Move, Skip and restore until a run credits them (`done`, `partial` or `overreached`), except that a made-up day takes no Skip, so a missed session moved onto today cannot be excused. A past day of the current Monday-to-Sunday week takes Move only, and only while unrun (`planned` or `missed`). A credited day, an excused past day and any day of an earlier week are final. There is no retroactive Skip, so a missed day stays `missed` and [PlanAdapter](app/Services/Run/Plan/PlanAdapter.php)'s adherence back-off stays honest. A move lands on a rest day of the session's own week: any from today through Sunday, or an earlier one only if a run landed on it. A Long, Tempo, Interval or Race session never lands beside another of those (the day it leaves turns rest and does not count), so a session can be left with no target and stays put. A move that also carries `skipped` or `pinned` is refused, and a refused edit answers 422 on `date` or `skipped`.

A skipped session exposes **restore**. [Plan](resources/js/pages/Plan.tsx) sends `{ skipped: false, pinned: false }`, restoring scoring eligibility and returning the day to regeneration's control. Uncredited days request no day narration; an edit that touches a credited current-week day refreshes its read under the existing fingerprint rule.

A day is moved (date), skipped or restored via [PlanController::update()](app/Http/Controllers/PlanController.php) (`PATCH /plan/sessions/{plannedSession}`). Skipping leaves the prescribed session as-is but pre-emptively excuses the athlete from being graded on it once the compliance pass reaches it. **Moving is a swap, not a re-date**: `planned_sessions` is unique on `(user_id, date)` and `WeekPlanBuilder` materializes all seven days of every week, so every target is already occupied — `update()` trades what the two days prescribe, each keeping its own calendar slot, and pins both. Per-segment editing is not exposed: segments are reconstructed from the row's stored intensity prescription. Any explicit edit auto-pins the row (so the next regeneration doesn't silently revert it) unless the request explicitly passes `pinned: false`, which a move never carries.

The workout that moves is `session_type`, `skipped`, the five stored intensity-prescription fields and `race_distance_m`. Date, phase, volume, clamp and grading history remain with each calendar row; a manual move keeps the prescription unchanged.

**A make-up links a run to a missed session.** A move from a past day, or onto a rest day a run already landed on, is a make-up ([SessionEditRules::isMakeUp()](app/Services/Run/Plan/SessionEditRules.php)). After the swap, inside the same lock and transaction, [MakeUpService::apply()](app/Services/Run/Plan/MakeUpService.php) stamps the emptied day `made_up_on` with the date the session moved to and points the made-up day back at it through `made_up_from_id`. It clears both days' clamp fields, so [EffectiveSession](app/Services/Run/Plan/EffectiveSession.php) never reads a stale ease, clears any skip the moved session carried, so the run it is linked to is credited rather than excused, and regrades both in full through `ComplianceScorer::verdictsFor()` and `applyVerdict()` rather than the upward-only `creditIfEarned()`. When the day's first run came before the moved session was shown, which the scorer reads from the shown-advice ledger (the revision shown last before that run must carry the moved session as its `original.session_type`), it grades the made-up day against the moved session with `advice_history: declared_after_run`, so it never teaches progression. A make-up onto a day still ahead, shown before its run, is graded on the shown advice like any other day. The scorer always grades the emptied day as rest, which takes its old `distance_score` out of next week's adherence ([[a-make-up-is-graded-against-the-moved-session]]). Once the lock is released, [MakeUpService::notify()](app/Services/Run/Plan/MakeUpService.php) marks the week for reconciliation from the earlier day, and [RenarrateAfterMakeUp](app/Actions/AI/RenarrateAfterMakeUp.php) invalidates the run narration and card flavor of both the made-up day and the emptied day, and re-requests today's briefing when the make-up lands on today or takes today's session away. A plain move onto or off today, or a skip or restore of today, re-requests the briefing too. Every one of these re-requests waits `AnalysisService::PLAN_EDIT_DELAY_SECONDS` (30 s) before its job runs, and a row already queued takes no second job, so a burst of edits narrates each row once, from the plan as it stands when the job starts. An edit that lands while the job is generating is not narrated again. `PATCH /plan/sessions/{plannedSession}` is throttled to 20 a minute; the per-athlete daily cost ceiling stays the backstop. The demo athlete stays rule-based. The emptied day's panel says "made up on" and the day, and season goals do not count it as honored rest. Feedback rows stay on their row and date.

All regeneration entry points serialize on the per-athlete `plan-reconciliation:{id}` lock from input gathering through persistence. Inside the write transaction, the periodizer reloads target rows before delete and upsert; rows newly pinned or settled survive, and one full rerun lays the rest of the week around them. Feedback is deleted only for rows that were actually removed.

Pin, block (`session_type = rest`) and delete were **cut** by the prototype-parity program's `PS4` (decision P23 — the prototype draws Skip and Move and nothing else). The `DELETE /plan/sessions/{id}` route and the `session_type` validation rule are gone with them; `pinned` survives as edit plumbing: `update()` sets it by default, and restoring a skipped future session explicitly clears it. `Periodizer::regenerate()` reads every pinned row in the horizon *before* building any week and never assigns a row to a pinned date; `WeekPlanBuilder` also skips any date before `$today` so **past weeks are never touched**. Regeneration is weekly ([routes/console.php](routes/console.php), `plan:regenerate` at Monday 00:26, after the existing Monday 00:00-00:21 cluster) plus on-demand (`POST /plan/regenerate`), on any change that reshapes a plan — setting a race ([RaceController::store()](app/Http/Controllers/RaceController.php)), clearing one ([RaceController::destroy()](app/Http/Controllers/RaceController.php)), or editing training preferences ([TrainingPreferencesController::update()](app/Http/Controllers/TrainingPreferencesController.php)) — and once more at the end of onboarding ([OnboardingController::store()](app/Http/Controllers/OnboardingController.php)) so a first plan exists the moment a user finishes signing up. Before that it didn't: those two triggers meant an athlete who connected on a Tuesday met an empty Plan tab and Home's "No plan yet." card until the following Monday. Onboarding is the right moment because `EnsureOnboarded` routes every new user through it, and it is the first point at which the preferences that shape a week — run days, sessions per week, the race goal — exist. Strava's backfill may still be running then, so a first week can be sized from [TrainingBaseline](app/Services/Run/Plan/TrainingBaseline.php)'s cold-start seeds; the backfill chain's last link ([KickoffRecapsJob](app/Jobs/AI/KickoffRecapsJob.php)) regenerates the moment that history lands, rather than leaving the cold-start week standing until Monday. It is a regeneration, not a gate: a failed backfill, a Strava outage or a genuine beginner with no activities would strand a gated athlete with no plan at all. The first week is described **once**, by whichever of two racers finishes second: onboarding narrates only if `users.backfilled_at` is already stamped, and the connect chain's last link ([KickoffRecapsJob](app/Jobs/AI/KickoffRecapsJob.php)) narrates only if a plan already exists — see [[strava-connect]]. Both go through [PlanNarrationRequester::requestForFirstWeek()](app/Services/AI/PlanNarrationRequester.php), which never invalidates, so the interleaving where both fire re-bills nothing and no ordering leaves the week silent. Until one of them fires there is no `Analysis` row, and `seasonPayload()` omits the season take with no row rather than shipping a `Pending` payload the UI would draw as a skeleton over work nobody queued. Regeneration works each athlete inside its own `try`/`catch`: one athlete's data must never cost every athlete after them their week, which is exactly what happened before — see below.

**A race the athlete has already run stops driving the plan.** `completed_at` was only ever stamped when a goal was superseded, so a race nobody replaced stayed `active()` forever and the periodizer kept planning against a day in the past. Since [PhaseSchedule::forRace()](app/Services/Run/Plan/PhaseSchedule.php) counts the weeks *left* until race day and `diffInWeeks` is signed, that count went negative and `array_fill()` threw — and because `plan:regenerate` looped without a guard, the whole run died on the first athlete holding one. [CloseFinishedRacesCommand](app/Console/Commands/Run/CloseFinishedRacesCommand.php) (`plan:close-finished-races`, daily 00:04, ahead of both `plan:score-compliance` and `plan:regenerate`) now retires a finished race so the plan falls back to the self-scaled arc; `forRace()` floors its week count at one regardless, since four callers reach it; and the command contains a per-athlete failure rather than propagating it. The race row is never deleted — a past race is still the athlete's record. Retiring a race is not an outcome: it stays `pending` until the athlete confirms what happened ([[a-race-outcome-is-confirmed-not-assumed]]).

Each regeneration deletes every unpinned, still-`planned` row across the *full* 12-week horizon before writing (not just the freshly-computed weeks), so a shrinking horizon — e.g. switching from self-scaled to a near-term race — cleans up stale far-future rows from the old mode rather than leaving orphans. A row that already carries a verdict is exempt and is not rewritten either: since [[a-day-is-scored-when-it-is-run]] compliance is persisted at ingest, so a regeneration triggered later the same day would otherwise delete the score today's run had already earned. Two things hang off a deleted row and [Periodizer::persist()](app/Services/Run/Plan/Periodizer.php) carries them across the delete rather than losing them: today's readiness clamp (`clamped_km`/`rest_clamped_at`, stamped by [RestClampRecorder](app/Services/Run/Plan/RestClampRecorder.php)) is copied onto the row that replaces it — [[the-eased-session-leads]] only holds if the clamp survives a same-day regenerate — and every `plan_day` [Feedback](app/Models/Feedback.php) row filed against a deleted id is deleted with it, so `/devtools/feedback` never lists a flag against a day nothing enforces anymore.

Ordinary recalibration keeps history. [PlanRecalibrationService::recalibrate()](app/Services/Run/Plan/PlanRecalibrationService.php) recomputes stored stream summaries and TRIMP with current HR zones, rebuilds weekly snapshots and regenerates the future plan, and nothing else: past prescriptions and the grades given against shown advice stay, and past plan-day narration is not marked stale. A unique per-user job runs after a profile, synced-zone or ingest max-HR change; `plan:recalibrate-history` provides the foreground path with `--user` and `--dry-run`, and excludes the demo account. The Plan tab keeps the last coherent plan visible behind a quiet pending notice, and recalibration spends no LLM tokens. The one-time pre-launch `coaching:reset` (removed 2026-10-08) rewrote and re-graded past days oldest first, once; see [[a-one-time-reset-rebuilds-history-before-launch]]. After it, any correction to history is scoped and verified, never a blanket rewrite.

The foreground command has no worker timeout and uses a 3600-second lease for both per-user locks. If it is interrupted before those locks are released, force-release them in Tinker before plan edits and recalibrations can resume: `Cache::lock("plan-reconciliation:{id}")->forceRelease()` and `Cache::lock("training-recalibration:{id}")->forceRelease()`, replacing `{id}` with the affected user's id.

The queued recalibration job has a 120-second timeout and a 150-second per-user lock. A benchmark of 1,008 activities completed in 34.66 seconds with 56 MB peak memory; linear extrapolation gives a rough 3,500-activity envelope before overhead, not a supported hard limit. The job retries until its ten-minute deadline; lock-contention releases do not spend the three-exception limit. With Redis `retry_after` set to 420 seconds, a job that repeatedly times out gets about two executions before that deadline. The run remains one atomic transaction, so an oversized history can still fail without progress. [[plan-recalibration-job-horizon]] records the timeout and runtime estimate, while [[plan-recalibration-retry-window]] records the retry window; [issue #1249](https://github.com/nukipratama/temari/issues/1249) tracks the durable follow-up.

### The plan reshapes now, the voice on a cooldown

A saved setting reshapes the plan immediately when its per-user regeneration lock is free. HTTP requests wait at most two seconds; if another regeneration still holds the lock, the setting remains saved and a plan regeneration is queued with an update message. Narration follows the completed plan. That covers setting a race, clearing one ([RaceController::destroy()](app/Http/Controllers/RaceController.php) — `/race` previously had no way to call a race off at all, so a wrong date was stuck until it passed while the plan kept building phases toward it; the goal is stamped `completed_at` rather than deleted, since an abandoned race is still part of the record), and editing training preferences. A race replaces the plan's whole structure (`PhaseSchedule::forRace()` supersedes the self-scaled arc, the season flips mode, the week's quality work changes with it), and run days decide the shape of every week `WeekPlanBuilder` emits — so saving either and seeing nothing happen until Monday made the setting look broken, while the race flash message said Temari would keep the plan honest against it.

Re-narrating the season costs an LLM call, and these are exactly the settings someone fiddles with repeatedly in one sitting, so [PlanRegenerationService](app/Services/Run/Plan/PlanRegenerationService.php) fires [PlanRegenerated](app/Events/PlanRegenerated.php), and [RequestPlanNarrationOnPlanRegenerated](app/Listeners/RequestPlanNarrationOnPlanRegenerated.php) routes settings-triggered narration through [PlanNarrationRequester::requestForCurrentWeekUnlessCoolingDown()](app/Services/AI/PlanNarrationRequester.php) behind a narration cooldown window. It guards **only** the voice — gating regeneration too would leave an athlete training against an arc their own goal had superseded. The manual regenerate button (which has its own hourly guard and exists precisely to refresh the voice) and plan:regenerate always request narration after regeneration.

The season take is **omitted from the payload** while it has no row at all: `Analysis::toPayload(null, ...)` reports `Pending`, which the UI draws as a skeleton — honest while a job is queued, false hope when none is. A `pending` row keeps its skeleton and a `failed` one keeps its empty state, because both are backed by something real.

## Readiness clamp — render-time, deterministic, not a narrator

This is the *within-the-day* half of the readiness reaction; the *within-the-week* half (a real deload) is in "Reacting to what actually happened" below.

[ReadinessClamp::apply()](app/Services/Run/Plan/ReadinessClamp.php) compares a stored session's implied intensity against the current [ReadinessCeiling](app/Services/Run/Metrics/ReadinessCeiling.php) and, when the stored session asks for more than the ceiling allows, returns a downgraded view plus a short templated explanation. That line is a **permanent floor**: a matching narrated line ([PlanClampVoiceNarrator](app/Services/AI/Narrators/PlanClampVoiceNarrator.php), kind `plan_clamp_voice`) may replace it in place, so a paused or cost-capped day still reads correctly. Narration is requested by shared daily-briefing side effects at the 00:01 kickoff and hourly catch-up replay, never by an ingest listener or a render. The voice fingerprint includes the saved readiness reasons; when an existing voice belongs to a different decision, the factual template is used. See [[the-clamp-explains-itself]]. [PlanController::index()](app/Http/Controllers/PlanController.php) applies advice to **today's row only**: a future day's readiness isn't knowable today, and clamping a whole training block by this moment's fatigue would defeat periodization. Before credit, today's recorded ease and today's still-unrecorded advisory both lead the day: `session_type`, `segments`, `distance_km` and pace are the advised session, and `eased_from` carries the replaced type, distance and reason as context ([[the-advised-session-leads-every-day]]). A pinned or Race row keeps its prescription and carries the advice as one `advice_note` line. An unpinned, uncompleted non-Race row may also persist today's adjustment and its `readiness_assessment` JSON on `planned_sessions`; today's feedback can replace or clear that saved adjustment. Pinned and Race prescriptions stay fixed but can carry current safety advice. Completed or already shown decisions are not regraded. A past recorded ease is read through [EffectiveSession](app/Services/Run/Plan/EffectiveSession.php), with `eased_from` naming what it replaced ([[the-eased-session-leads]]). Both [PlanPageAssembler](app/Services/Run/Plan/PlanPageAssembler.php) and [CurrentWeekPlanBuilder](app/Services/Run/Plan/CurrentWeekPlanBuilder.php) use the same clamp contract. While recent training is hydrating, the assessment leaves load and activity evidence unknown; current pain or illness feedback still produces safety advice.

[Readiness::assess()](app/Services/Run/Metrics/Readiness.php) distinguishes literal recency from actual training stress. It reviews analyzed activities from the previous seven local dates and counts a session as demanding when it lasted at least 90 minutes, or at least 60 minutes and 1.5 times the median duration of the athlete's earlier runs in that window; it also counts at least 10 minutes in HR zones 4–5. If HR zones are absent, usable lap or whole-run GAP pace at or faster than 105% of an available personal threshold pace counts when it covers at least 10 minutes. The absolute and relative duration cutoffs are conservative signals, not clinical thresholds. When duration is known, demanding recovery hours run from the session's end. One demanding session ending within 24 hours or more than one ending within 48 hours restricts full-dose quality; an easy or rest day does not restart that interval, and 45 hours since an otherwise-clear demanding session is not a veto.

**The load balance is context, never a verdict.** The athlete sees it as `fresh`, `steady` or `heavy` ([[load-numbers-are-named-as-running-load]]). The stored `fatigued` or `overreaching` state (both shown as heavy) sets no ceiling of its own and only counts as supporting load for a reported concern; it is unknown for its 42-day warm-up. The volume guard compares actual km-to-date with the week's prescribed km-to-date ([BriefingContext::prescribedKmToDate()](app/Services/Run/Story/BriefingContext.php)), not with last week, and the personal-range guard compares unrounded weekly TRIMP with the eight weeks before the current one, only when the athlete is also ahead of the prescription. See [[a-load-label-supports-a-concern-it-never-decides-one]].

Current-day recovery feedback is optional. Pain or illness advises full rest, severe fatigue or soreness allows easy only, and moderate fatigue/soreness restricts full-dose quality. Mild feedback alone does not replace quality without supporting load evidence; stale feedback is retained in the assessment inputs but not applied. A mixed sleep, fatigue, and soreness report is not treated as contradictory because those are independent dimensions. The saved `readiness_assessment` contains the inputs and reason codes behind a recorded adjustment, and recommendation snapshots use policy version 2 for redesigned decisions. Older shown or completed recommendations are not broadly regraded.

[RestClampRecorder](app/Services/Run/Plan/RestClampRecorder.php) refuses a new recorded adjustment once the athlete has run today, including a full Rest ceiling reached after that run. Clamp writes and `plan_clamp_voice` requests come from shared daily-briefing side effects, including hourly catch-up replay; the ingest listener does neither. If a clamp still renders after a run on an uncredited day, it keeps the recorded assessment and its matching morning narration or templated explanation, so post-run feedback cannot replace the cause of the decision. Catch-up may stage a missing narration row without dispatch, but preserves an existing completed explanation.

Quality work (Tempo/Interval) runs its full dose at `QualityOk`. At `ModerateOk`, an existing hard-minute prescription keeps its type and pace band with 75% of the hard minutes, rounded down; this is a planning heuristic, not a physiological threshold. At the mildest `ModerateOk` triggers alone ([ReadinessClamp::isMildModerate()](app/Services/Run/Plan/ReadinessClamp.php): mild fatigue or soreness, or fair or poor sleep, with supporting load and no trigger that caps the day by itself) the session instead keeps all its minutes at a pace 3% slower (`MILD_QUALITY_PACE_SLOWDOWN`, a heuristic), and grading judges against that slowed pace because it is what the shown segments carry. Goal-pace work at a mild trigger keeps its goal pace and takes the 75% cut, and a time trial at `ModerateOk` becomes an easy run of the trial distance, so it counts as skipped and gets its one retry ([[easy-and-long-runs-are-capped-by-heart-rate]]). The effective dose is saved under `readiness_assessment.adjustment.quality_dose` and [EffectiveSession](app/Services/Run/Plan/EffectiveSession.php) supplies the same prescription to rendering and grading. Legacy rows without a prescription retain their Easy clamp. A Race row at `ModerateOk` keeps its event distance with conservative effort advice. Long needs `ModerateOk`, and Easy needs the floor above `Rest`. Dose and event advice use deterministic copy so a cached explanation of a different session replacement cannot describe them.

**A pace-only ease for the two cases `apply()` leaves untouched.** An Easy day that already clears `EasyOnly`, or a Long day that already clears `ModerateOk` (marathon-pace long runs included), gets no type/distance downgrade — but only just clears it, so [ReadinessClamp::paceEaseApplies()](app/Services/Run/Plan/ReadinessClamp.php) still asks for a gentler pace: the slow end of the easy band, [TrainingPaceCalculator::easySlowEndSecPerKm()](app/Services/Run/Metrics/TrainingPaceCalculator.php) exposing the slow end of the same E band whose midpoint is the `easy` guide, without moving that guide. [RestClampRecorder](app/Services/Run/Plan/RestClampRecorder.php) records it once, the same way as `clamped_km`/`rest_clamped_at`, onto `planned_sessions.eased_pace_sec_per_km`, and [EffectiveSession](app/Services/Run/Plan/EffectiveSession.php) reads it back (`isPaceEased()`): type and core km are untouched, only the pace `PlanRenderer::dayPayload()` builds the day's segments with. It is rule-based only — no `plan_clamp_voice` request and no `DayClampedNotification`, since the day it applies to is exactly the boundary case [ClampNarrationContext](app/Services/Run/Plan/ClampNarrationContext.php) also has nothing to explain for — and grading is untouched, since [SessionIntentJudge](app/Services/Run/Plan/SessionIntentJudge.php) grades easy/long against marathon pace or the heart-rate cap, never the easy prescription. See [[the-eased-session-leads]].

**A day has no narrated read** ([[a-plan-day-has-no-narrated-read]]). The day card carries [SessionIntentJudge](app/Services/Run/Plan/SessionIntentJudge.php)'s verdict from [[a-day-is-graded-on-distance-and-intent]], read straight off the `PlannedSession` row (`intent_verdict`/`intent_evidence`, written by [ComplianceScorer::applyVerdict()](app/Services/Run/Plan/ComplianceScorer.php)). No narrator sees the enum or the raw evidence: [IntentOutcome](app/Services/Run/Plan/IntentOutcome.php) words the verdict as a clause (`intent`, what [PlanContextTool](app/Services/AI/Agent/Tools/PlanContextTool.php) hands the briefing and run narrators) and the evidence as a sentence with every comparison already made (`intent_detail`). An easy day's limit is the *fastest* pace it allows, so a raw pace-vs-limit pair read backwards and inverted a hit (#1357). The judge grades an easy day on grade-adjusted pace; the detail quotes the moving pace the card shows and names the hill-adjusted one only when the two differ by `IntentOutcome::EFFORT_ADJUSTED_MIN_GAP_SEC` (5 s/km) or sit on opposite sides of the limit. The card's own "averaged X/km, past the Y/km ceiling" result note follows the same rule. [OutcomeLabels](app/Services/AI/Narrators/OutcomeLabels.php) rejects a post-run briefing that labels the outcome (`too_hard`, "intent hit", any snake_case field) through `ChatCallOptions::validator`: one rewrite, then the job fails rather than store it.

**Once the day is credited the advice disappears.** [Readiness::assess()](app/Services/Run/Metrics/Readiness.php) caps to `EasyOnly` on `ranToday` alone, so finishing the session is itself what clamps it: a tempo run at 102% rendered beside *"today backs off to easy"*, which reads as though the athlete should have done less. It once became a menu for a second outing instead; nobody asked for one. [PlanRenderer::dayPayload()](app/Services/Run/Plan/PlanRenderer.php) now applies no advisory clamp to a credited day, and a credited run explains itself in a `result_note` worded from [IntentOutcome](app/Services/Run/Plan/IntentOutcome.php) (unplanned hard effort, an eased tempo run anyway, a strong-concern day run hard, or an unknown effort that "counts its distance only"). The day states its own result through `judgedDayResult()` in [lib/plan.ts](resources/js/lib/plan.ts) — the recorded prescription against what was run. The narrated `plan_clamp_voice` line goes with it: it was written for the forecast, and re-narrating would bill an LLM call from a GET. See [[a-credited-day-shows-its-result]].

## Volume redistribution — a recompute, not a day-swap

Rather than moving a specific day's volume to another specific day (which risks an awkward doubled-up load), Home and `/plan` recompute the current week's remaining unpinned, non-past **easy** days from `(week's target km) - (already completed) - (km of pinned days from today on) - (today's now-fixed km) - (km of the long, tempo and interval days still ahead)`. [CurrentWeekVolumeProjector::project()](app/Services/Run/Plan/CurrentWeekVolumeProjector.php) reuses the activity-date read and shares the calculation between both surfaces. It applies one continuous scale factor to each remaining easy day's own core km; key sessions never resize. No band bucketing: [SegmentGenerator](app/Services/Run/Plan/SegmentGenerator.php) accepts an arbitrary target distance for any session type, so a reduced day lands on its exact figure rather than snapping to a small set of discrete sizes. Actual surplus earlier in the week may shrink future easy runs; missed or readiness-reduced distance never enlarges them ([[no-automatic-mileage-debt]]). A recorded ease lowers both the week's target and today's fixed contribution by the same effective km. An unrecorded clamp still subtracts its smaller fixed contribution from the un-eased target. This is render-only.

The scale factor is capped at `VolumeRedistributor::MAX_SCALE` (1.0) and floored at `MIN_SCALE` (0.7). Missed or reduced volume is written off rather than shifted onto the remaining days, while actual surplus can reduce future easy volume without shrinking a day below 70% of its original ask. Volume never crosses a week boundary either — a missed week becomes a re-entry deload (below), not a debt added to the next one.

## Reacting to what actually happened

The three sections above are all *render-time* reactions within one week. The generation-time reaction is [PlanAdapter](app/Services/Run/Plan/PlanAdapter.php), which [Periodizer::regenerate()](app/Services/Run/Plan/Periodizer.php) consults before it builds a single week.

**Matching runs to sessions — written when the day is earned, settled when it ends.** Both paths go through [ComplianceScorer](app/Services/Run/Plan/ComplianceScorer.php), which is one class because the trailing-week context window it builds is load-bearing (see below). At ingest, [creditIfEarned()](app/Services/Run/Plan/ComplianceScorer.php) writes a day's verdict the moment a run lands on it, but **only ever upward** — anything short of credited stays `Planned`, so a partial day can never freeze low, while a run arriving after the daily pass already wrote the day off still lifts it. On ingest, re-ingest, revision or a late upload the earned score never moves down, but the intent verdict and stimulus evidence are rewritten whenever the recomputed reading differs (equal score, revised, split or delayed recordings). See [[a-day-is-scored-when-it-is-run]]. A deletion is the one exception: [DeleteIngestedRunAction](app/Actions/Run/DeleteIngestedRunAction.php), shared by [CleanupDeletedActivityJob](app/Jobs/Strava/CleanupDeletedActivityJob.php) and a resync that re-types a run to a non-run sport, re-grades the day from the surviving runs in either direction through [regradeAfterDelete()](app/Services/Run/Plan/ComplianceScorer.php), so an `overreached` duplicate can drop to `done` and a past day with no run left drops to `missed`, while an excused day stays `skip`. It then marks plan reconciliation and trend snapshots dirty from the run's date ([[decoupling-describes-a-run-and-a-deletion-re-grades-its-day]]). [ScoreComplianceCommand](app/Console/Commands/Run/ScoreComplianceCommand.php) (`plan:score-compliance`, daily at 00:09, before the Monday 00:26 `plan:regenerate`) then settles what is left: every still-`Planned` row that's now past-due, writing back `status`, `compliance_score` and `ran_anyway` via [SessionMatcher::scoreRange()](app/Services/Run/Plan/SessionMatcher.php). It doubles as the backfill mechanism for any historical backlog — the query is "any Planned row that's now past, regardless of age," so there's no separate backfill command. [SessionMatcher::scoreFor()](app/Services/Run/Plan/SessionMatcher.php) grades km actually run against km prescribed as a continuous `round(completedKm/plannedKm * 100)` score. **Each session type is credited by what it asks of the athlete.** A `Tempo` or `Interval` day counts its **best single run**, since the stimulus is one continuous effort and two easy outings are not a tempo session. A `Long` day **sums** its runs, because that volume genuinely accumulated, but reaches `done` only when one run carried `LONG_RUN_SINGLE_RUN_FRACTION` (70%) of the ask — otherwise the score keeps the honest ratio while the status reads `partial`, and the row carries a line saying the distance arrived in pieces. A Long day the clamp eased to an easy run (a recorded `clamped_km`) is graded as an easy day instead, with no single-run rule ([[an-eased-long-day-is-graded-as-an-easy-day]]). `Easy`, `Rest` and `Race` days sum, unchanged. Both figures come off one query in [completedKmByDate()](app/Services/Run/Plan/SessionMatcher.php), and the matcher reads each date's own session type itself so the three callers building `plannedKmByDate` cannot drift out of step with it. See [[a-credited-day-shows-its-result]]. The bands: `<35` is `missed`, `35-84` is `partial`, `85-129` is `done`, `>=130` is `overreached` (see [PlannedSessionStatus](app/Enums/PlannedSessionStatus.php); `isCredited()` counts `done`/`partial`/`overreached`, not `planned`/`missed`/`skip`). **A credited day is then judged on the session's intent too.** [SessionIntentJudge](app/Services/Run/Plan/SessionIntentJudge.php) reads the effective session's pace targets against the day's runs (best-effort windows for tempo, laps for intervals, overall pace against marathon pace for easy and long, heart rate able to rescue a slow block; for an athlete with zones of their own, easy and long runs are judged on the heart-rate cap instead, see [[easy-and-long-runs-are-capped-by-heart-rate]]) and returns `hit`, `missed`, `too_hard` or `unknown`. A hit needs a window, lap or recording covering about 90% of the requested work, every Main threshold or marathon block of a tempo day together and the reps needed of an interval day, and partial evidence is `unknown`. On a watch's plain kilometre grid the pace window fits inside one rep or block, so on a longer day a window at pace is `hit` only when heart rate at or above the work zone covers the requested minutes, and otherwise `unknown`, never `missed`; a window short of pace is still `missed` ([SessionIntentJudge::interval()](app/Services/Run/Plan/SessionIntentJudge.php), [SessionIntentJudge::tempo()](app/Services/Run/Plan/SessionIntentJudge.php)); and a quality block more than 5% quicker than target reads `too_hard` rather than being rewarded; [SessionMatcher::withIntent()](app/Services/Run/Plan/SessionMatcher.php) folds it in, so a `done` distance that missed its intent reads `partial` with its score capped at 84, running too hard reads `overreached`, and `unknown` grades on distance alone. The status stays `overreached` either way, but the page tells the two apart: a day overreached on intent rather than distance carries a `ran_hot` flag and a `result_note` from the judge's evidence ([PlanRenderer](app/Services/Run/Plan/PlanRenderer.php)) and reads `ran hot`. The plain km ratio is kept beside it as `distance_score`. See [[a-day-is-graded-on-distance-and-intent]]; `plan:regrade-season` regrades the current season's past days under that rule. A day the athlete pre-emptively excuses (`PATCH /plan/sessions/{id}` with `skipped: true`) always resolves to `skip` regardless of km, with a null score — as does a day the readiness clamp downgraded to a full rest, via [PlannedSession::isExcused()](app/Models/PlannedSession.php). That second case has to be *recorded* rather than recomputed: the ceiling is derived from `TrainingLoad::summary()`, which counts the day's own runs, so the clamp that fired at 08:00 no longer exists at 00:09. [RestClampRecorder](app/Services/Run/Plan/RestClampRecorder.php) writes `rest_clamped_at` through shared daily-briefing side effects, including catch-up replay, before any run that day, never from the ingest listener or a render, so an athlete who took the rest the card prescribed isn't graded against the session it replaced. Only the full-rest clamp needs this; the other downgrades leave enough km on the day to credit on their own. That same write is where the athlete is told: it fires a `plan_clamp` inbox row ([[notification-inbox]]) carrying the clamp's own explanation, so a step-down is a record rather than something that existed only while the plan page still rendered it. A rest day asks for nothing, so it always reads `done` with a null score; `ran_anyway` separately records whether an activity was logged on it anyway, without changing the status. [PlanController](app/Http/Controllers/PlanController.php) and [CurrentWeekPlanBuilder](app/Services/Run/Plan/CurrentWeekPlanBuilder.php) read the stored `status` column as the primary source of truth; `SessionMatcher::statuses()` is the render-time fallback for the rare row still `Planned` despite being past-dated (the daily command hasn't reached it yet) **and for today, which the daily command deliberately never reaches**. Today is graded on the same km ratio but only ever upward — anything short of credited floors back to `Planned`, since falling short isn't decidable until the day ends while clearing the bar can't be undone by the hours left in it. That resolution is render-only; the persisted column is settled the morning after, and afterwards only a credited run raises it or a deletion re-grades it. See [today-credits-when-earned](docs/decisions/today-credits-when-earned.md). [PlanAdapter::previousWeekAdherencePct()](app/Services/Run/Plan/PlanAdapter.php) averages last week's persisted `distance_score`, never the intent-widened score (each day capped at 100 first, so one `overreached` day can't mask other missed ones), excluding rest, still-unscored and `skip` days, and defaults to perfect adherence when nothing was scoreable at all.

**One decision per week, safety first.** [PlanAdapter::decide()](app/Services/Run/Plan/PlanAdapter.php) is pure and returns exactly one [AdaptationReason](app/Enums/AdaptationReason.php), evaluated in priority order: readiness bottoming out at `Rest` (reported concerning pain or illness only), then a mostly-missed week, then a week run harder than it was written, then missed key stimulus, and only then race-pace feedback. Chasing a goal time can therefore never talk the plan past a red flag. While any run in the 42-day load window still awaits hydration, [PlanAdapter::forWeek()](app/Services/Run/Plan/PlanAdapter.php) reads no load at all, the same gate the plan page applies. Monotony and strain describe the week but never deload it ([[monotony-and-strain-describe-a-week-they-never-deload-it]]).

**A judged day states what it asked and what was run.** Prescribed km is not stored on the plan row: [PlanController::index()](app/Http/Controllers/PlanController.php) recomputes it on every load against the athlete's *current* baseline, which is right for the week ahead and wrong for a week already graded. [ComplianceScorer](app/Services/Run/Plan/ComplianceScorer.php) therefore measures each day against the baseline **as it stood that day** (`TrainingBaseline::forUser()` has always taken an `asOf`; nothing passed a historical one), and records the figure in `planned_sessions.prescribed_km` beside the verdict. A judged day then pairs the two facts by side rather than by figure — *"asked 6 km · 5:32/km"* then *"ran 5 km · 6:43/km"* in [DayDetail](resources/js/components/plan/DayDetail.tsx)'s `DayHeadline` via the shared `AskedRanResult` (see [resources/js/components/plan/DeltaPair.tsx](resources/js/components/plan/DeltaPair.tsx)) — both recorded facts, each labelled, no arrows since an arrow means the plan changed and this is what happened, so the pair still reads correctly when the athlete went long (*"asked 9 km"* / *"ran 12 km"*) — while a day still ahead shows the ask alone, prescription first in both. Without the as-of baseline a day scored weeks late was graded against fitness the athlete had since built: a fixture with two accumulated weeks marks a 3.4 km day against 14.3 km. Once the day is credited, its pace pairs up the same way: [SessionMatcher::ranPaceSecPerKmFromRuns()](app/Services/Run/Plan/SessionMatcher.php) reads elapsed time over distance across the identical runs `creditedKm()` grades the km with — the best single run for Tempo/Interval, the day's total otherwise — so the asked line's pace is the effective target and the ran line's is the credited runs' own pace, never the two mixed on one line.

**A real deload, not a note.** The first four reasons rewrite the current week's phase to [PlanPhase::Deload](app/Enums/PlanPhase.php) before any row is built. That is structural in both directions at once: `WeekPlanBuilder` emits no quality slots for a `Deload` week, and because the rewrite lands *before* `volumeMultipliers()` runs over the arc, the week's km drop to `previous build's final multiplier * 0.65` with no separate scale factor to keep in sync — and the weeks after it stop counting the turned-down week as a Build week. A `Taper` week is exempt — it is already a planned reduction counting down to race day.

**A missed week comes back smaller.** Adherence below `MISSED_WEEK_ADHERENCE` produces the same deload rather than carrying the missed volume forward. Simulated end to end in [tests/Feature/Plan/MissedWeekAdaptationTest.php](tests/Feature/Plan/MissedWeekAdaptationTest.php): a 4-session, 28.3 km build week with nothing logged against it is followed by a 16.6 km deload week carrying zero quality sessions.

**A week run harder than it was written drops a quality session.** The adapter reads *how* last week's sessions were executed, not only whether they were done. [PlanAdapter::previousWeekExecution()](app/Services/Run/Plan/PlanAdapter.php) counts the easy-effort days, `Easy` days and `Long` days with no marathon-pace block, whose runs held more time past the heart-rate cap than [EasyEffort::tooHard()](app/Services/Run/Plan/EasyEffort.php) allows: over 15 minutes, or 20% of moving time when the day's runs total under 75 minutes, of 30-second rolling-average heart rate more than 5 bpm above the top of zone 2, read from the per-run figure on each stream summary ([[easy-and-long-runs-are-capped-by-heart-rate]]). Steady-segment decoupling no longer makes a `Long`, `Tempo` or `Interval` day ragged: heat, duration and hydration move it, and it stays on the run as durability information ([[decoupling-describes-a-run-and-a-deletion-re-grades-its-day]]). At `RAGGED_DAYS_MIN` such days the week returns `RanTooHard` with a `quality_delta` of -1. One merely ragged day is a bad morning and is ignored.

Past that, a **single** easy-effort day past [EasyEffort::egregious()](app/Services/Run/Plan/EasyEffort.php), double the ragged line (30 minutes, or 40% of a run under 75 minutes), is the whole verdict on its own. The real prod week that first put a single-day bar there rested on such a day: one Saturday missed and one Sunday long run spending 92.2% of its moving time in Z3 and above, scoring exactly 50% adherence — not *below* `MISSED_WEEK_ADHERENCE` — so a count-only rule called that week `steady`, "nothing to change, the plan stands". The *other* number quoted from that same week, 47.1% decoupling, turned out to be a strap dropout read as cardiac drift (see [[stream-analysis]]).

Because sessions are matched to days and not to runs, a day's runs are read together and the day counts once. A run carrying no heart-rate stream reads as *no signal* rather than as a clean day: it has no figure, so the test cannot fire. This is deliberately **not** a deload: the volume stands, only the intensity comes off. It sits above race-pace feedback, so an athlete behind their goal time who ran the week too hard gets one *less* quality session, not one more.

**The race goal changes no work.** With an active race, [RiegelProjector](app/Services/Run/Metrics/RiegelProjector.php)'s projected finish is compared to the stored `goal_time_sec` for display only. A projection slower than the goal no longer adds a quality session, and one faster than the goal beyond `RACE_GAP_MARGIN` is named [`AdaptationReason::AheadOfRacePace`](app/Enums/AdaptationReason.php) by [PlanAdapter](app/Services/Run/Plan/PlanAdapter.php) with a `quality_delta` of 0. The stated ambition stays visible, and race-day pace and marathon-pace blocks come from the athlete's supported fitness ([[one-race-model-drives-the-plan]], [[race-ambition-is-shown-and-capacity-is-prescribed]]), except the goal-pace work of an on-track or ambitious goal in its last weeks ([[goal-pace-work-in-the-last-weeks]]), and an unsupported goal's at its stepping-stone pace ([[a-stepping-stone-for-an-unsupported-goal]]). Season-goal generation deliberately keeps using the unadapted `qualitySlotCount()`, so a mid-season adaptation doesn't move the goalposts it was scored against.

**Volume and stimulus are separate adaptation signals.** `adherence_pct` averages the prior week's capped `distance_score`, while `stimulus_adherence_pct` counts Long, Tempo and Interval verdicts only from eligible rows (shown, unchanged quality advice). A full-distance easy run on a quality day therefore completes volume but records a missed stimulus when the shown advice can be verified. One such miss holds the quality block; two misses in the settled three-week window remove one slot, never stacking catch-up work. During an open week only closed days contribute, so today's row cannot become a miss and a later run can still earn the day. Unknown or missing advice history, `Unknown` verdicts, unscored rows and explicitly skipped rows do not drive intent adaptation. Existing grades remain untouched, and distance scores continue to count independently. See [[plan-adaptation-responds-to-stimulus]].

**Being ahead does not touch the quality block at all** (#933). Being ahead of a goal time is fitness feedback on a prescription that is working — the plan already self-corrects in the athlete's favor since prescribed paces derive from recent performance — not a red flag, so `AheadOfRacePace` carries `quality_delta: 0` the same as `Steady`. Removing a session on top of a faster prescription pushed the wrong way twice, and on a four-session week (a single quality slot on the phase baseline) it read as the plan asking an athlete *beating* their goal to stop training for it. Only `RanTooHard`, a real fatigue signal from [PlanAdapter::previousWeekExecution()](app/Services/Run/Plan/PlanAdapter.php) below, still empties the block. The `AdaptationReason` case stays and is still surfaced (headline "ahead of pace") so the athlete and the narrators can tell it apart from an ordinary `Steady` week, and so [SustainedAheadOfRacePace](app/Services/Run/Plan/SustainedAheadOfRacePace.php) can watch for it holding — see "Season narration" below.

**Recorded, not recomputed.** The verdict is written to a [PlanAdaptation](app/Models/PlanAdaptation.php) row, `unique(user_id, week_start)`. `/plan` reads that row rather than re-deciding, so a deload triggered on Monday still explains itself on Thursday after the athlete's readiness has recovered. When the deload takes a race season's week under its volume floor, the row also carries that floor as `volume_floor_km` and the detail line names it: the floor is a target the load guard may break, but never silently. A block holding its increases for unscored load stamps `increases_held` on the row the same way, and the detail line says the build is waiting. The copy lives on the enum ([AdaptationReason::headline()/detail()](app/Enums/AdaptationReason.php)), never in the database.

**Material evidence reconciles the current plan.** [DispatchPostRunAnalysis](app/Listeners/DispatchPostRunAnalysis.php) and [ScoreComplianceCommand](app/Console/Commands/Run/ScoreComplianceCommand.php) mark a user's affected date through [PlanReconciliationService](app/Services/Run/Plan/PlanReconciliationService.php). [ReconcilePlanJob](app/Jobs/Run/ReconcilePlanJob.php) coalesces concurrent activity, uses a per-user lock, ignores dates older than the previous week, and calls [Periodizer::regenerateIfChanged()](app/Services/Run/Plan/Periodizer.php); unchanged adaptation fingerprints do not rewrite the plan. A mid-week reconciliation can only move safety downward: it never removes a deload or restores reduced quality while that week is open. A settled key-session hit can release a prior-week quality hold once it becomes the current week's evidence. A changed plan fires [PlanRegenerated](app/Events/PlanRegenerated.php), and for recently active athletes [RequestPlanNarrationOnPlanRegenerated](app/Listeners/RequestPlanNarrationOnPlanRegenerated.php) refreshes the season narration through its adaptation-aware fingerprint, and a current-day plan read waits until this reconciliation completes. The Monday regeneration remains the recovery path for anything missed by the event or daily pass.

**Prescriptive, not clinical.** The Plan tab renders a standing not-medical-advice disclaimer on every load, adaptation or not ([Plan.tsx](resources/js/pages/Plan.tsx)): a one-line footer, the headline plus a link to the full statement and its scope on `/training-disclaimer` (see [[plan-page-leads-with-this-week]]). The headline is served from [TrainingDisclaimer](app/Support/TrainingDisclaimer.php) rather than held locally, so the public [[legal-pages]] and this tab cannot drift into two different positions. The tone gets to be assertive about numbers precisely because the clamps above stay in force underneath it.

## Render-time segments — never frozen into the row

[SegmentGenerator::coreKmFor()](app/Services/Run/Plan/SegmentGenerator.php) is the only place a `session_type` becomes an actual kilometre figure, combining the athlete's *current* long-run baseline with a phase-derived volume multiplier — the direct successor to `DistanceBandKm::kmFor()`, before `distance_band`/`pace_band` were retired as stored columns. [PlanController::index()](app/Http/Controllers/PlanController.php) recomputes this fresh on every page load (never reading a stored km), so a week regenerated weeks ago still displays honestly against the athlete's fitness today. `SegmentGenerator::generate()` goes one step further for the full segment breakdown: even the *shape* of an Interval day (its rep count) is pace-dependent, so nothing about a day's structure is ever persisted — see the "Shared session-structure logic" section above. The one number generation does stamp is `volume_multiplier`, and it is not fitness: it is where the week sits in its season's arc, which no render window can re-derive. `fall_off_tilt` is stamped for the same reason: it is the fit at generation, which a later read cannot re-derive.

**Easy and long runs are run under a heart-rate cap.** For an athlete whose zones come from Strava, a manual edit or an observed peak, every Easy day and every Long day with easy running carries `hr_cap_bpm`, the top of zone 2 ([PlanRenderer::heartRateCapOf()](app/Services/Run/Plan/PlanRenderer.php)). Home and the Plan day lead with "under {cap} bpm" and show the pace as a hint, "about m:ss/km", with a long run told its pace may slow late ([targetLabel()](resources/js/lib/plan.ts), [sessionHint()](resources/js/lib/plan.ts)); a marathon-pace long run keeps its pace target and caps the easy running around the block. Config-default zones leave `hr_cap_bpm` null and pace the target. See [[easy-and-long-runs-are-capped-by-heart-rate]].

**Shared with Home.** [PlanRenderer](app/Services/Run/Plan/PlanRenderer.php) holds the phase→volume-multiplier grouping and per-day payload, while [CurrentWeekVolumeProjector](app/Services/Run/Plan/CurrentWeekVolumeProjector.php) applies the same current-week volume adjustment to [CurrentWeekPlanBuilder](app/Services/Run/Plan/CurrentWeekPlanBuilder.php) (Home's `weekPlan` prop) and [PlanPageAssembler](app/Services/Run/Plan/PlanPageAssembler.php). Their current-week workout types, distances, segments and totals therefore use the same projection. A Peak/Taper/Deload week's multiplier is relative to its place in the season's arc, which both callers read off the row itself. **A week reads its phase and multiplier off one row** ([PlanRenderer::weekRow()](app/Services/Run/Plan/PlanRenderer.php)): the latest-dated unpinned row, falling back to the latest-dated row when the whole week is pinned. Regeneration never rewrites a pinned row, a settled one, or a date already behind it, so a week can hold a stale row from an older generation beside fresh ones — a pinned Monday still reading `Build` while the adapter has just turned the week into a reactive `Deload`, or Monday to Thursday run under `Build` when a Friday on-demand regeneration deloads the rest. Every regeneration writes forward to the week's end, so the last row it could still own is the one carrying its most recent decision; reading the first row by date, as this used to, let one stale Monday cancel the deload on every surface, and a majority vote would let the four already-run days do the same. The phase-sequence recompute stays as the fallback for a window still holding a row written before generation stamped the multiplier, and it is why both callers query the identical `HISTORY_WEEKS` window.

## Season — the arc this plan belongs to (Slice 7)

The Plan tab's top-of-page summary section is the same periodized arc viewed at a higher zoom, not a separate page (`Season IS the training block` — see the v2 program's locked decisions). [SeasonService::ensureCurrent()](app/Services/Run/Plan/SeasonService.php) is called both from `PlanController::index()` (a fresh user's first page view already has a season) and from `Periodizer::regenerate()` (the weekly job and on-demand regeneration keep it in lockstep with the plan's own mode). `SeasonService::peekCurrent()` is the read-only counterpart the [[profile]] page uses instead — it returns the current season if one already exists, `null` otherwise, and never creates, updates, or closes a `Season` row. A self-scaled `Season` runs a fixed 12 weeks (matching `HORIZON_WEEKS`) and auto-cycles into a fresh one on expiry; a race-oriented one ends on `race_date`. The season also carries `anchor_weekly_volume_km` — the trailing weekly mean frozen at the moment the arc opened, which every prescription in it ramps off. `SeasonService::reanchorIfCollapsed()` is its only mid-season write: downward only, only past a 25% collapse, and only when the athlete also ran under 75% of what the last six settled weeks prescribed. At rollover, an athlete who followed the prescription keeps at least the previous anchor, so following the plan never lowers it. See [[the-arc-is-anchored-once]]. Setting or clearing a `RaceGoal` mid-season closes the current season early (`ends_at` moves to the day before) and opens the other mode at the next call — never a gap, never an overlap, since the mode check always compares the CURRENT active race against the latest season's `race_goal_id`.

`SeasonGoal` rows generate at creation. A race season adds its block goals on the first call on or after block open, stamped as `seasons.block_goals_appended_at` so later calls skip the database. Because a web request and a queued regeneration can both reach [SeasonService::ensureCurrent()](app/Services/Run/Plan/SeasonService.php) for the same athlete, the whole call runs in one transaction holding a lock on the user row and re-reads the current season inside it. Goal rows are written with `firstOrCreate`, with `unique(season_id, metric)` on `season_goals` as the database backstop. The existing `unique(user_id, starts_at)` on `seasons` backs season creation: a season insert that still collides returns the season that won. See [[gamification]] for the full list and the rest-day reward mechanism that isn't a `Badge`. A race season with fewer block rows from its start through race week than the full block serves a fixed under-ready line once on the Plan page, stamped as `seasons.under_ready_noted_at` ([SeasonService::takeUnderReadyLine()](app/Services/Run/Plan/SeasonService.php)); see [[the-block-opens-on-a-computed-date]].

### Season-wide summary — the nested timeline (`V0` fork 3, rebuilt by `PS4`)

`PlanController::index()`'s own `weeks` payload only ever covers a rolling `HISTORY_WEEKS`/`LOOKAHEAD_WEEKS` window (3 history + current + 4 lookahead), not the full season — real scope for a season-wide phase-progress bar and week-by-week volume timeline, deliberately left out of `S4` (see that slice doc's "Deliberately scoped OUT"). [SeasonSummaryBuilder::build()](app/Services/Run/Plan/SeasonSummaryBuilder.php) closes that gap with a separate, season-wide read model (`seasonSummary` Inertia prop): one entry per week from `Season::$starts_at` to `$ends_at`, each carrying its phase, its `general`/`block` zone, a `history`/`current`/`lookahead` type, a `planned_km` figure, a `sessions` count, and (once a [WeeklySnapshot](app/Models/WeeklySnapshot.php) exists for that week) an `actual_km`. The current week's row takes its `planned_km`, phase and `eased_from_km` from [CurrentWeekPlanBuilder](app/Services/Run/Plan/CurrentWeekPlanBuilder.php), whose week total comes from [CurrentWeekKm::forUser()](app/Services/Run/Plan/CurrentWeekKm.php): the week as it ends if the athlete follows the plan from today, the credited km of past days, today's credited km once run or else its shown km, and the shown, trimmed km of later days ([[the-week-total-is-the-week-the-plan-asks-for]]). When the trim absorbs an overrun it equals the projector's week target, a missed day lowers it, and a floor-bound trim leaves it above; the narrator's `get_planned_sessions` reads the same shown km for today and the rest of the week. So the header and Home agree with the day rows beneath it, today's ease included; for a reactive deload the eased-from figure is the arc's own km ([[the-advised-session-leads-every-day]], [[the-eased-session-leads]]). Future weeks keep the arc figure, since their readiness is not knowable yet (#1433). `SeasonSummaryBuilder::adherencePct()` is the season header card's headline figure — the mean of every persisted `compliance_score` inside the season, so it covers weeks the page no longer renders day rows for.

`planned_km` is computed the same deterministic, season-start-anchored way [SeasonService::generateGoals()](app/Services/Run/Plan/SeasonService.php) already sizes its `SeasonGoal` targets — `PhaseSchedule`/`WeekPlanBuilder`/`SegmentGenerator`, never a read of materialized `PlannedSession` rows. Those rows only cover the periodizer's own rolling `Periodizer::HORIZON_WEEKS` (12-week) horizon and get deleted/recreated on every weekly regeneration, so they're the wrong source for a stable, whole-season figure — the same reasoning that already keeps `SeasonGoal` targets off of them. The trade-off: a week's `planned_km` won't reflect a real-time adaptation (e.g. an in-week deload) the way the day-by-day schedule below it on the page does.

**Frontend**: `PS4` replaced fork 3's two flat panels (`SeasonPhaseBar`, `SeasonWeekTimeline`) and the flat day-card list beneath them with the prototype's single nested timeline (decision P22).

[SeasonHeaderCard](../../resources/js/components/plan/SeasonHeaderCard.tsx) heads the page as a one-line band: week X of N with the current phase, the season adherence figure and the phase ribbon. Opening it shows the season's date span, one bar per phase (height by that phase's mean weekly volume, so the bar chart traces the season's real arc), the one-time under-ready line when the season payload carries one, and Temari's season narration. Its `phasesOf()` builds the bars from the phase sequence the season actually has, so a self-scaled season's repeating Build/Deload cycle renders honestly rather than being forced into a fixed Base/Build/Peak/Taper four (see `App\Enums\PlanPhase`'s own docblock on which phases exist in which mode).

**The phase ribbon** ([PhaseRibbon](../../resources/js/components/plan/PhaseRibbon.tsx)), bordered in `border-border` to hold its shape against either ground, is one cell per week of `seasonSummary`, season start to race day: a flat neutral "maintain" fill for every `zone: general` week regardless of its own `phase` (the self-scaled cycle alternates Build/Deload before the block opens, and showing that would read as noise), and a `PHASE_COLORS` fill per `zone: block` week. It reads `zone` off each week directly: the per-week flag is already the boundary, so the season payload carries no block-open date. No number ever appears in it: hovering, tapping or focusing a cell is the only way to see its phase name, which is also the cell's accessible name, and the current week is marked by drawing every week up to and including it solid, with every week still ahead faded (`opacity-40`) — the solid/faded edge is "now", not a separate ring or dot. A self-scaled season carries no `block` week at all, so it renders nothing. "Maintain" is a display label only: the season payload's own `zone` value stays `general`.

[SeasonTimeline](../../resources/js/components/plan/SeasonTimeline.tsx) sits beneath it: one week laid out open, then a list of every week in the season ([[plan-page-leads-with-this-week]]). There is no rail, no dots and no folded "weeks behind/ahead" clusters any more.

**The open week** is a [WeekView](../../resources/js/components/plan/WeekView.tsx), this week by default. Under its header (week number, dates, marks, target, sessions and the adherence of its scored days) it stacks a "1 done · 2 missed" line (with "so far" on the current week), the current week's adaptation note in full as a callout, a [WeekStrip](../../resources/js/components/plan/WeekStrip.tsx) of seven tiles and a day panel. Each tile carries the weekday, the km (what was run, else what was asked, `—` for rest) and one word: today is filled lime, a missed day outlined in ember, a run day tinted leaf, rest muted, and the selected tile carries its own ring. The strip is a tab list, so arrow keys, Home and End move the selection. The panel opens on the day `/plan?day=` asked for when it falls in the week (and scrolls to it), else today, else the first session still to run, else the first day. No week has a volume chart, since the tiles carry the km.

**The weeks list** ([WeeksList](../../resources/js/components/plan/WeeksList.tsx)) is one row per `seasonSummary` week: its number, dates, a phase pill (grouped by `phaseGroupKey`, so every `zone: general` week reads "maintain"), the km (run for a week behind, planned otherwise) and, for a week behind that the page holds day rows for, its adherence. The current week's row says so. A row for one of the weeks inside `PlanController`'s render window (3 behind, this week, 4 ahead) is a button: picking it swaps that week into the open view, and a "back to this week" pill in its header returns. A week outside the window is a plain row with nothing to open, so the payload is unchanged. A `/plan?day=` date inside another loaded week opens that week and that day.

On desktop the Plan page uses the same [PageContainer](../../resources/js/components/ui/PageContainer.tsx) width as every other page (`max-w-column-wide` from 1280px); a narrower Plan column read as inconsistent beside them.

**A week that is not an ordinary week says so in its header**, in words rather than in a bar colour: a `deload week` chip when the week's phase is `Deload`, and a `race week` chip on the week the goal race falls in. The open week's header carries them. The race week is resolved client-side by [isRaceWeek](../../resources/js/lib/plan.ts) against the `race.race_date` the page already holds — the season summary spans weeks far past the periodizer's day-row horizon, which is exactly where a race sits, so a per-week server flag would be the wrong source. The chip is what makes the week legible without reading a legend.

A day's detail lives in one place, [DayDetail](../../resources/js/components/plan/DayDetail.tsx), which the day panel renders: the eased-value change rows, the point, the advised session as the headline with its eased-from context (a pinned or Race day shows its prescription and an advice note), credit and result notes, a [SessionBarGraph](../../resources/js/components/plan/SessionBarGraph.tsx) (the session's segments, width by minutes and height by zone, with interval repeats collapsed into one "N× Interval" legend block), a link to what was actually run, and the Move/Skip actions. Its `DayHeadline` heads the panel.

Phase fill colors are the `PHASE_COLORS` export in [chartTokens.ts](../../resources/js/lib/chartTokens.ts), validated distinct via the dataviz skill's palette checker and deliberately drawn away from `PALETTE.overloaded`/`gassed`/`chill`, which are already committed to per-run Mood colors; zone fills reuse the existing `HR_ZONE_COLORS` ramp. Shared payload types, the adherence mean and the label maps live in [lib/plan.ts](../../resources/js/lib/plan.ts).

## Plan narration — voice only, layered on top

`PlanSeasonVoice` narrates what the rules above already decided, never re-deciding it, through the standard AI narration pipeline (see the `temari` skill's narration reference, `.claude/skills/temari/references/narration.md`): `PlanSeasonVoiceNarrator` under [app/Services/AI/Narrators/](app/Services/AI/Narrators/) and its `AnalyzeRowJob` subclass under [app/Jobs/AI/](app/Jobs/AI/). The clamp line is covered under the readiness clamp above.

**The week's own adaptation display never went through narration.** The headline, detail sentence
and deload/quality chips `WeekView` and `SeasonHeaderCard` show for the current week come
straight off the periodizer's own [`PlanAdaptation`](app/Models/PlanAdaptation.php) row and
[`AdaptationReason::headline()`/`::detail()`](app/Enums/AdaptationReason.php) — deterministic, not
LLM voice. A `plan_week_voice` narrated line used to sit alongside it as the old week row's
collapsed "Temari's take"; the owner cut it 2026-09-17 (#947) since it added no information the
deterministic display didn't already carry. See [[llm-triggers]]'s Retired surfaces for what
removing the `AnalysisType` case did to existing `plan_week_voice` rows.

**There is no per-day read** since 2026-10-07 ([[a-plan-day-has-no-narrated-read]]). The stored `plan_day_voice` rows and the flags on them were deleted, and no ingest, edit, make-up, return or regrade asks for one.

**Season narration attaches to `Season`**, requested on every dispatch for recently active athletes. Almost everything about a season's material is fixed at creation (a mode switch opens a new `Season` row rather than mutating this one), so an already-`Done` row is normally left alone on `AnalysisService`'s own idempotency alone. The time-varying material fingerprint includes [SustainedAheadOfRacePace](app/Services/Run/Plan/SustainedAheadOfRacePace.php)'s signal (#933) and the current week's recorded adaptation reason/deload, so Monday changes and mid-week reconciliations invalidate exactly when the tool context changes. A never-fingerprinted `Done` row reads as changed, so every season re-narrates once rather than silently carrying a blurb that never had a chance to mention the current adjustment.

**The demo fills the season take rule-based.** Its Plan page goes through `PlanNarrationRequester::ensureDemoFilled()`, the path its manual "Reread" already resolves through, and `plan:regrade-season` ([RegradeSeasonCommand](app/Console/Commands/Run/RegradeSeasonCommand.php)) regrades without writing any narration.

**Season narration is dispatched from `Periodizer::regenerate()`'s two callers, never from `Periodizer.php` itself** — [PlanController::regenerate()](app/Http/Controllers/PlanController.php) (manual, through the [PlanRegenerated](app/Events/PlanRegenerated.php) event and its sync [listener](app/Listeners/RequestPlanNarrationOnPlanRegenerated.php)) and [RegeneratePlanCommand](app/Console/Commands/Run/RegeneratePlanCommand.php) (the weekly cron), via [PlanNarrationRequester](app/Services/AI/PlanNarrationRequester.php). Literally dispatching narration inside `Periodizer.php` would contradict its own "no LLM call anywhere in this feature" heritage; keeping the requester one layer up preserves that boundary while still tying narration to the exact moment the underlying facts change. `RegeneratePlanCommand` narrates the season of every athlete [RecentlyActiveUsers](app/Actions/AI/RecentlyActiveUsers.php) returns — demo excluded, and only someone who opened the app inside the active window ([[narration-follows-the-athlete-not-the-run]]) — while the regenerate half stays exactly as free as before and still runs for everyone. The narration half is real per-user LLM cost, so it's classified `BILLING` in [DemoBillingExclusionTest](tests/Feature/Console/DemoBillingExclusionTest.php) even though the command's own regenerate call is unconditional.

**The manual Regenerate button still carries a real rate limit.** A full regenerate dispatches the season narration row — real LLM cost per click — so `PlanController::regenerate()` checks a dedicated one-hour cooldown ([PlanRegenerateCooldown](app/Services/Run/Plan/PlanRegenerateCooldown.php)) before calling the periodizer, started immediately rather than waiting for the async narration job to finish (closing the queue-latency window where two rapid clicks could both slip through). It's a standalone `Cooldown` key, not `Analysis::cooldownKey()` reused — every narration row's own completion unconditionally starts its own shorter (15-minute) cooldown in `AnalysisService::markDone()`, so sharing the key would have this longer window silently overwritten within moments. The weekly cron starts the same cooldown after its own regenerate (so a manual click right after Monday's auto-run is still correctly rate-limited) but never checks it — the cron always runs.

### No season track on the page

`PP3` cut the `SeasonTrack` tier module (P24): the prototype's Plan screen draws a
`SeasonHeaderCard` with a single progress line, not a pip rail. The season-scoped reward engine
behind it — `GrantSeasonUnlocksAction`, the `season.{id}.track_{N}` grants and the
`season.tiers_kept_from_past_seasons` count — went with the rest of the unlock system, since
nothing had rendered any of it since P24. What remains is the `SeasonGoal` set itself, resolved
live by [SeasonGoalResolver](../../app/Services/Gamification/SeasonGoalResolver.php) for
[[profile]]'s season card, the only screen that draws a goal. Plan's `season` prop is the season
frame alone, with no goals and no season record.

The per-goal `GoalCard` grid under the season summary is gone: P24 replaced the tier module with
the prototype's single progress line, and `W2` swept the orphaned component. The week-grained
lifetime streak (`WeeklySnapshot::consecutiveWeekStreak()`) does not render here either; its
page-level wrapper, `streakPayload()` on what is now `SeasonPayloadBuilder`, had no caller and is deleted.
`PlanPageAssembler` calls `seasonPayload()` only.
