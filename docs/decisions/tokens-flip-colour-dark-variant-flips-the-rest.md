# Tokens flip a colour; the `dark:` variant flips everything else

**Status:** Accepted (documented 2026-09-05)

## Context

Two mechanisms in this codebase can make a value depend on the ground.

The **semantic token layer** is the one the app was built on. A component writes
one class, `bg-card`; [app.css](../../resources/css/app.css) defines
`--color-card` as `#f1f5f8` and redefines it under `[data-theme='dark']`. The
component never learns which ground it is on. One definition site, generated by
[build-tokens.mjs](../../resources/brand/build-tokens.mjs), consumed by roughly
400 components.

**Tailwind's `dark:` variant** is the other. The component writes both values,
`ring-foreground/5 dark:ring-foreground/10`, and the ground difference is
encoded at every call site that needs it. It arrived with the vendored shadcn
primitives in `F3` and appears in ten lines, all of them in
[button.tsx](../../resources/js/components/ui/button.tsx),
[card.tsx](../../resources/js/components/ui/card.tsx) and `toggle.tsx`.

Those ten lines were not working. Tailwind v4 defaults `dark:` to
`@media (prefers-color-scheme: dark)`, and this app switches grounds with
`data-theme` on `<html>` — never a `.dark` class, never the media query. So
every `dark:` utility was firing on the reader's **OS setting**, independent of
the ground they chose in Settings. A user on the dark ground with a light OS got
none of them; a user on the light ground with a dark OS got all of them.

The obvious repair is to point the variant at `data-theme`. That leaves the
question of whether `dark:` should exist here at all.

## Decision

Wire the variant to the ground:

```css
@custom-variant dark (&:where([data-theme='dark'], [data-theme='dark'] *));
```

and split the two mechanisms by what they are each able to express:

- **A ground difference in a colour value is a semantic token.** Never
  `bg-cream dark:bg-sky` — that is `bg-card`.
- **A difference that is not a colour value may use `dark:`**: an opacity, a
  ring width, a whole property.

All ten existing utilities are the second kind, so nothing migrates.

## Why not tokens for everything

The stricter rule reads better than it works. `card.tsx`'s live case is
`dark:ring-foreground/10` — the *same* token at a different **alpha**. A token
cannot hold that: the dark block is literal-hex-only (see
[ink-grounds-derived-not-listed](ink-grounds-derived-not-listed.md) and the R1
guard that enforces it), so expressing it means minting a `--color-card-ring`
and hand-compositing the alpha into a hex twice, once per ground. Ten times
over, for ten lines that were never the problem.

## Why not `dark:` for everything

Three things the token layer gives that a utility cannot.

**One definition site.** A token changes in one place and all consumers follow.
A `dark:` pair changes wherever it was written, so drift is per call site.

**The audit can classify it.** `grounds.json` splits every token into fixed and
reactive, and `DesignTokenContrastTest` scores each kind only against the
grounds it can actually land on. A `dark:` background *is* scraped into the
panel registry — `muted/0.5` and `input/0.3` come from `button.tsx`'s own
`dark:hover:` utilities — but it is registered as `over: paper`, with nothing
recording that the rule applies to one ground only. It is scored against the
whole paper set. That is the same fixed-versus-reactive confusion `#720` fixed
for tokens, reintroduced through a mechanism the classification does not model.
Not unaudited: **mis**-audited. Harmless today only because both entries carry
`text: []`, so nothing scores text on them.

**Raw-palette drift is impossible.** `npm run check:palette` rejects
`bg-gray-700`. Nothing rejects `dark:bg-gray-700`.

## Consequences

Ten utilities begin tracking the chosen ground rather than the OS. The visible
delta is card ring opacity across 34 `<Card>` call sites and two button
variants, for readers whose OS and app ground disagree.

The mis-audit above is left standing. Teaching the panel scan that a
`dark:`-prefixed background applies to one ground only is the real repair, and
it is worth doing the next time that registry is touched for another reason.

The rule is **not** enforced by a guard. All ten current utilities comply, so a
check would have nothing to catch, and "is this utility a colour" is awkward to
decide mechanically — `dark:bg-*` is a colour, `dark:ring-*/N` is an alpha on
one. It is written down in the `temari` skill, which is what gets read before a
component is written.
